## 1. What the feature is for
An invoice a supplier sends to AnalyticsFab (the accountant's monthly fee, a SaaS invoice, the Swiss fiduciary): a document reviewed by OCR, a partner, the supplier's invoice number, dates and a due date, an amount with VAT in CHF/EUR/SEK, and the bank transaction that paid it. v3 keeps it as its own **payable** module (D8) instead of an expense row: it has a due date, it is unpaid until a bank transaction is linked, and its VAT feeds the declarations. The accountant books it; the app shows what is due, links the payment and puts the PDF in the month's package under `supplier-invoices/`.

## 2. Behaviour — rules as numbered statements

### 2.1 What v1 did
- R1 A supplier invoice = `partnerId` (partner with SUPPLIER role, `isSupplier` computed column; `'Supplier not found'` 404 otherwise), `invoiceNumber` (the supplier's), `invoiceDate`, `dueDate`, `currency`, `subtotal` + `vatAmount` + `totalAmount`, `description`, `notes`, ≥ 1 line (`lineNumber`, `description`, `quantity`, `unitPrice`, `amount`, optional `vatCodeId`, `basAccountId`) (`schema.prisma` l.1037–1116; `SupplierInvoiceCreateSchema`).
- R2 Validation: `total = subtotal + vat` within **0.01** (`'Total amount must equal subtotal + VAT amount'`); `subtotal ≥ 0`, `vatAmount ≥ 0`, `totalAmount > 0`; line `quantity ≥ 0`, `unitPrice ≥ 0`, `amount ≥ 0` (zero allowed: "free item"); unique line numbers (`'Line numbers must be unique'`); currency ISO-3; `supplierId` (legacy) or `partnerId` required (`'Either supplierId or partnerId is required'`). The line-sum-equals-subtotal check is a `refine` that always returns `true` (comment: "performed in the API") — and the API does not perform it either: dead rule.
- R3 Currency defaults: body `currency` → partner `defaultCurrency` → tenant base currency (`route.ts` l.180). New suppliers get `defaultCurrency` `SEK` and `paymentTermDays` 30 (`suppliers/route.ts` l.114–115).
- R4 SEK base at create and at every `PUT`: the **latest** `exchangeRate` row from invoice currency → base (`orderBy date desc`), stored with its `exchangeRateDate`; `subtotal`, `vatAmount`, `totalAmount` each multiplied; same currency → rate 1 (`route.ts` l.172–205; `[id]/route.ts` l.131–172). Not the rate of the invoice date, and recomputed on edit — not immutable.
- R5 No own number: the supplier's `invoiceNumber` is the reference everywhere (list, matcher, journal description). `EntitySequence` reserves the prefix `SI` (`SI25-001`) but no route uses it for supplier invoices.
- R6 Status machine (schema comment l.1059, routes): `PENDING` (create) → `APPROVED` (approve; permission `approve SupplierInvoice`; `'Only PENDING supplier invoices can be approved'`) → `PAID` (set by reconcile when fully paid); `CANCELLED` exists in the comment and in the delete rule; `REJECTED` exists only in `SupplierInvoiceUpdateSchema.status` and in a test — no route sets it. Edit only `PENDING` (`'Only PENDING supplier invoices can be edited'`), lines replaced wholesale on PUT; delete only `PENDING` or `CANCELLED`, hard delete (`'Only PENDING or CANCELLED supplier invoices can be deleted'`).
- R7 Approval posted a journal entry in one DB transaction with the status change: Dr each line's `basAccountId` (error `'No BAS account specified for line: {description}'` — so a line without a BAS account made approval fail), Dr `2641` input VAT when `vatAmount > 0`, Cr `2440` for the total, entry date = `invoiceDate`; posting failure rolled the approval back (`posting-service.ts` l.281–347; approve test "should rollback on posting failure").
- R8 Payment recording = linking a bank transaction, two routes: (a) `POST /api/supplier-invoices/[id]/reconcile` {bankTransactionId, allocatedAmount, notes}: refuses `PAID`/`CANCELLED` (`'Cannot reconcile a paid supplier invoice'`), **requires the same currency** (`'Currency mismatch — Supplier invoice and bank transaction must use the same currency for reconciliation'`), checks Σ allocations on the transaction ≤ |amount| (`'Allocated amount exceeds available transaction amount'`, returns `available`), checks Σ payments on the invoice ≤ total (`'Total payments exceed supplier invoice amount'`, returns `remaining`); (b) the generic `POST /api/banking/transactions/[id]/reconcile` with `type: 'SUPPLIER_INVOICE'` — same checks **without** the currency rule (`reconcile/route.ts` l.474–573). Both create a `SupplierInvoicePayment` {allocatedAmount Decimal(19,4), currency = invoice currency, notes, reconciledAt/By} and set `PAID` + `paidDate` when `determinePaymentStatus` says PAID (tolerance SEK 0.50 / CHF 0.05 / EUR 0.05 on underpayment, note `Rounding adjustment: …`, see H8 fixture `v1-rounding-tolerances.json`). Partially paid invoices keep their status (no `PARTIALLY_PAID`; comment at `reconcile/route.ts` l.180); `paidAmount` / `remainingAmount` are computed from payments in the list (`route.ts` l.74–88), never stored.
- R9 Unreconcile deletes the payment row and reverts `PAID → APPROVED` only when no payments remain (`unreconcile/route.ts` l.51, 410–425).
- R10 Payment-side journal (`Dr 2440 / Cr 1920`) was dead: `postPaymentJournal` returns `null` when called inside a transaction, which every reconcile route does (`posting-service.ts` l.577–583).
- R11 Matching suggestions for an outgoing transaction: supplier invoices `status = APPROVED` only, `deletedAt null`, **no payment rows**, `invoiceDate` within ±5 days of the booking date, amount within 1 % (+5 % when cross-currency, converted through the ECB table at each side's date); score = reference (invoice number in message/recipient/details +40; partner name +25; token of the number +15) + amount (exact +40, < 1 % +30, < 5 % +20, else +10) + date (same +30, ≤ 2 d +25, ≤ 5 d +15, else +5) − 10 for currency mismatch without a reference match; HIGH when reference match and ≥ 60 or ≥ 80, MEDIUM ≥ 50, LOW below (`matching.ts` l.318–469, 750–851). Detail in H3. Note the date window on `invoiceDate` (not `dueDate`): an invoice paid at its 30-day due date is outside the ±5-day window and is never suggested — a bug for payables.
- R12 Documents: `POST /api/supplier-invoices/[id]/documents` uploads the PDF as `DocumentType.SUPPLIER_INVOICE` with `linkType` ∈ {ORIGINAL (default), RECEIPT, SUPPORTING, CORRESPONDENCE, GENERATED}; `GET` lists them. From the documents side, `create-entity` builds a `PENDING` supplier invoice from OCR: `invoiceNumber` ← `invoiceId` (required: `'Invoice number is required'`), `invoiceDate` ← `invoiceDate` else today, `dueDate` ← `dueDate` else **today + 30 days**, `vatAmount` ← `totalTax` else 0, `totalAmount` ← `invoiceTotal`/`total`, title ← `vendorName`/`merchantName`/file name, lines ← OCR line items else one line = subtotal; partner required (inline creation ADMIN only) (`create-entity/route.ts` l.226–306).
- R13 Swiss VAT declaration (H6): input VAT (form ref. 400, "Vorsteuer auf Material- und Dienstleistungsaufwand") is summed from supplier-invoice **lines** whose `vatCode.country = 'Switzerland'`, invoices `APPROVED` or `PAID`, `invoiceDate` in the period, VAT **recomputed** as `line.amount × rate / 100` (not the stored `vatAmount`) (`swiss-vat/route.ts` l.211–297).
- R14 UI: list KPIs `Total Invoices`, `Pending Approval`, `Outstanding` (PENDING + APPROVED totals in base currency), `Paid Total`; columns `Invoice #`, `Supplier`, `Invoice Date`, `Due Date`, `Amount`, `Status`, `Actions`; status badges PENDING (yellow, clock), APPROVED (green, check), PAID (blue, dollar), CANCELLED (grey, ban); detail shows `VAT`, `Paid`, `Remaining`, document preview (`'Document preview unavailable'`), confirm prompts `'Approve this supplier invoice?'`, `'Delete this supplier invoice? This action cannot be undone.'`. **No overdue computation anywhere** — due date is a column and a filter only.

### 2.2 What v3 must do (D8, §3.6)
- R15 A supplier invoice is a **payable**: `partner` (supplier type), supplier's `invoice_number` (unique per partner), `invoice_date`, `due_date` (default `invoice_date + partner.payment_terms_days`, 30 if unset), `currency` (default partner default currency), `amount_net`, `vat_amount`, `amount_total` (= net + VAT within 0.01), `amount_base` + `rate` + `rate_source` + `rate_date` written once (ECB of `invoice_date`, D3/D4 — replaces R4), one **BAS category** with alias (`Acc` for the accountant, `Ut` for a SaaS…), optional `vat_registration` (SE or CH) when the VAT is deductible there, `note`, the **document** (OCR-reviewed, business key), `document_missing` flag.
- R16 **Lines only when a VAT split needs them** (§3.6): by default no lines; the owner may add lines when one invoice carries two VAT rates or two categories; then Σ line net = `amount_net` and Σ line VAT = `vat_amount` are enforced (the rule v1 declared and never ran, R2).
- R17 **Status derived, never typed**: `unpaid` (no link), `partially paid` (0 < Σ allocations < total), `paid` (Σ allocations ≥ total − tolerance), `overdue` (unpaid/partially paid and `due_date < today`), `cancelled` (explicit flag with a reason — the only typed state, for an invoice withdrawn by the supplier; a credit note from the supplier is a new negative payable linked `credits`). Replaces R6/R8/R9.
- R18 No approval (R7 dropped): the gate is "document reviewed" (OCR review overlay of the documents module) and the audit log. Nothing is posted; the BAS category + the link are what the accountant needs (D1).
- R19 Payment = a `link(kind=justifies, allocated_amount)` between the paying bank transaction and the invoice (D18), created from the transactions workbench, from the invoice page, or by accepting a suggestion. Allocation ≤ invoice open amount; Σ allocations on the transaction ≤ |amount|; **cross-currency allowed** (a CHF invoice paid from the SEK account) — the allocation is in the transaction currency, compared in SEK base, the difference beyond tolerance is an exchange-difference line as in H8 §9.2. Tolerance rule as v1 (R8). One invoice ↔ many transactions (instalments) and one transaction ↔ many invoices (a batch payment) both allowed.
- R20 Suggestions (H3) use the **due date** as the primary date anchor for payables (`due_date ± 5 days`, then `invoice_date ± 5`), fixing R11.
- R21 Dashboard action item "supplier invoices due": unpaid/partially paid, sorted by `due_date`, with `overdue` in red; counts and open totals in SEK base (feature-inventory §3.14).
- R22 VAT for declarations: `vat_amount` and `vat_registration` on the invoice (or per line when split) feed the Swedish moms prep and the Swiss form field mapping (H6): the stored VAT is used, not recomputed (fixes R13's recomputation drift on rounded invoices).
- R23 Package (D13): the invoice's document goes to `supplier-invoices/` of the month of `invoice_date` (and the month of payment appears in the bank sheet with the link); the generated summary's supplier sheet lists supplier, invoice number, dates, amount, VAT, paid via which bank line, status.
- R24 Partner 360 (feature-inventory §3.3) shows the supplier's invoices with open totals; partner defaults (currency, payment terms, BAS category, VAT registration) pre-fill the form.

## 4. Algorithms / formulas
1. **Base amounts**: `rate = ECB(currency → SEK, invoice_date)` (weekend/holiday → last available, `rate_date` recorded); `amount_base = round(amount_total × rate, 2)`; `vat_base = round(vat_amount × rate, 2)`; SEK → rate 1. Never recomputed; a wrong date means a new invoice record (correction) or a manual `rate_source = manual` override at creation only.
2. **Due date default**: `invoice_date + payment_terms_days(partner)`; v1's OCR path used `today + 30` when the OCR had no due date — v3 uses the partner's terms from the invoice date and marks the field "defaulted" for review.
3. **Paid test**: `open = amount_total − Σ alloc_in_invoice_currency`; paid when `open ≤ 0` or `0 < open ≤ tolerance(currency)` (SEK 0.50 / CHF 0.05 / EUR 0.05; underpayment only); the note format `Rounding adjustment: {symbol} {diff} ({name} rounding tolerance)` is kept on the link.
4. **Cross-currency allocation**: transaction in `T.currency`, invoice in `I.currency`. `alloc` is entered in `T.currency`; converted to `I.currency` through SEK base (`alloc_base = alloc × T.rate`; `alloc_in_I = alloc_base / I.rate`); `open` compared in `I.currency` with the tolerance of `I.currency`; difference beyond tolerance → exchange-difference line on the link (category per H8 §9.2). Example: invoice 1 000 CHF at 10.75 (base 10 750); paid −10 700 SEK from AF SEK → alloc_in_I = 995.35 CHF → open 4.65 CHF > 0.05 → owner confirms "paid, exchange difference 50 SEK" or leaves 4.65 CHF open.
5. **Overdue**: `status ∈ {unpaid, partially paid} ∧ due_date < today(tenant zone)`; days overdue = `today − due_date`.
6. **Duplicate guard**: same partner + same invoice number → refuse with a link to the existing one; same document hash → documents module (H7).
7. **VAT split lines**: when lines exist, `vat_amount = Σ line.vat_amount` and `amount_net = Σ line.amount_net`, each line `vat_amount = round(amount_net × vat_rate, 2)` where `vat_rate` comes from the registration's schedule (never a magic number — bas-accounting "Never").

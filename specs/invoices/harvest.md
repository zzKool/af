## 1. What the feature is for
Once a month the owner bills his client for the days worked: one invoice per client and month, days × the contract rate of the period, in the client's currency (CHF for the Swiss client), with the client's purchase-order / supplier references printed, 8.1 % Swiss VAT when the Swiss registration applies, a PDF that goes to the client and to the accountant (`InvoiceAF_VA26-001.pdf`), and a number the client's accounts-payable can read (`VA26-001`). The app must know which invoices are still open, what was paid (from the bank), and — for the Swiss VAT return — in which quarter each invoice is declared. Corrections are credit notes, never edits. Quotes exist in the owner's practice (a proposal before a contract) but v1 never built them.

## 2. Behaviour — rules as numbered statements

### H1 — model, lifecycle, numbering, credit notes, payments
- R1 v1 ran **two invoice models side by side**: `Invoice`/`InvoiceLine` (old, L885-989; header VAT rate, no discount, no credit notes) and `InvoiceV2`/`InvoiceLineV2` (L2532-2687). All `/api/invoices/*` routes and the UI write only V2; the dashboard counts (`app/dashboard/page.tsx:67,85`), the bank matcher (`lib/banking/matching.ts:204`), the entity graph, document links and **the Swiss VAT report** (`swiss-vat/route.ts:85`) read only the old model. An invoice created in v1's editor therefore never reached the VAT return or the dashboard. (abandoned mid-migration)
- R2 Statuses (`lib/validation/invoices.ts` L17-25): `DRAFT, FINALIZED, SENT, PAID, PARTIALLY_PAID, OVERDUE, CANCELLED`; `PAID` and `CANCELLED` are terminal. Server transitions L232-240: `DRAFT → FINALIZED | CANCELLED`; `FINALIZED → SENT | PAID | PARTIALLY_PAID | CANCELLED`; `SENT → PAID | PARTIALLY_PAID | OVERDUE | CANCELLED`; `PARTIALLY_PAID → PAID | OVERDUE | CANCELLED`; `OVERDUE → PAID | PARTIALLY_PAID | CANCELLED`. The detail page's copy (L132-138) omits `FINALIZED → PARTIALLY_PAID`. Every transition is a manual button; `OVERDUE` is never set by the system (no job, grep confirms). `sentDate` is stamped on `→ SENT`, `paidDate` on `→ PAID` (`status/route.ts` L70-76).
- R3 Only `DRAFT` invoices can be edited (`[id]/route.ts` L209-215, "Only draft invoices can be edited") or deleted (L449-454, "Only draft invoices can be deleted"); lines are replaced wholesale on edit (L316-363). Nothing locks `FINALIZED` fields other than this check; `invoiceNumber` is editable while draft (L218-234, duplicate → 409 `Invoice number "X" already exists`).
- R4 The **number is typed by the client**: `POST /api/invoices` takes `invoiceNumber` (schema L122, `min(1).max(50)`), checks uniqueness per tenant (L97-111) and stores it. `GET /api/invoices/next-number?partnerId=` returns a suggestion by calling `generateInvoiceNumber` — which **increments the sequence on every call** (`next-number/route.ts:45`); the form calls it on every partner change (`useInvoiceV2Form.ts` L253-268, L306). Result: gaps every time a draft is abandoned or the client switched, and a draft already carries a number. `check-number` only reports availability.
- R5 `generateInvoiceNumber(partnerId, tenantId)` (L158-260): prefix = `partner.code || 'INV'`; year = **current calendar year** (`new Date().getFullYear()`, L174 — not the invoice date); format `${prefix}${yy}-${String(n).padStart(3,'0')}` (L238) → `VG25-001`, grows past 999 without truncation; one `InvoiceSequence` row per `(tenantId, partnerId, year)` (`@@unique`, L1005) created lazily, `P2002` on create → re-read; `lastNumber` incremented in a `Serializable` transaction (`maxWait 5000, timeout 10000`); retries `MAX_RETRIES = 5` with `RETRY_DELAY_MS = 50 × (attempt+1)` on `P2034`/`P2028`; final error `Failed to generate invoice number after 5 attempts: …`; partner must belong to the tenant and not be soft-deleted (`Partner not found or does not belong to your tenant`). Nothing resets or edits a sequence; there is no settings UI.
- R6 Reference fields are **copied onto the invoice at creation** (`route.ts` L193-199) with the client's own labels: `contractNumber ← partner.fixedContractReference` (label `clientReferenceLabel`, default `Fixed Contract Reference`), `vendorId ← partner.supplierNumber` (label default `Supplier Number`), `purchaseOrderNumber ← project.clientReference` (label default `PO Number`). The form applies the same defaults on partner/project change (`useInvoiceV2Form.ts` L291-294, L317-333). Printed only when both value and label are present (`invoice-template.ts` L505-534). `lib/invoices/metadata.ts` (a `Consultant: name (supplierNumber)` text builder) has no caller.
- R7 Partner defaults applied on selection (`setPartner` L271-314): `currency ← partner.defaultCurrency || 'CHF'`; `paymentTermDays ← partner.paymentTermDays || 30`; `useBusinessDays ← partner.paymentTermsType === 'BUSINESS_DAYS'`; due date recomputed; `vatRate` of **every existing line ← partner.defaultVatRate** when set; project, PO reset. Form defaults (L166-194): date today, 30 days, business days on, currency `CHF`, language `en`, one empty line `quantity 1, quantityType DAY, unitPrice 0, vatRate 0`.
- R8 Due date (`calculateDueDate` L141-164): calendar mode = invoice date + N days; business mode = walk forward one day at a time counting only Mon–Fri until N counted (no holidays). Schema refinement: `dueDate >= invoiceDate` ("Due date must be on or after invoice date", L169-178). Manual override by date picker is allowed and not re-validated against the terms.
- R9 Line validation (L41-94): `description 1..5000` required; `quantity 0..999999.9999`; `quantityType ∈ DAY, HOUR, UNIT, FIXED, SESSION, KM, MONTH` (default `DAY`; `FIXED` forces quantity 1 in the editor); `unitPrice 0..999999999.99`; `discountType ∈ PERCENTAGE, FIXED` with the matching value required ("Discount amount is required when discount type is specified"); `vatRate 0..100` default 0; `periodStart/End` optional. Invoice: `lines.min(1)` ("At least one line item is required"), `currency` 3 letters default `CHF`, `language ∈ en, sv, fr, de` default `en`, `notes/internalNotes ≤ 10000`, `paymentTerms ≤ 1000`, invoice-level `discountType/discountPercent` (0..100). A credit note must carry `relatedInvoiceId` ("Credit notes must reference an original invoice").
- R10 Base-currency amounts are written at create/update from the **latest exchange rate in the table** (`orderBy date desc`, L152-158), not the rate of the invoice date; when no rate exists the base amounts stay `null`; same currency → rate 1. (bug vs D3)
- R11 Approval (`approve/route.ts`): any non-cancelled, not-yet-approved invoice can be approved (`isApproved, approvedBy, approvedAt`); approval can be revoked only while `DRAFT` or `FINALIZED`. Nothing in the lifecycle depends on approval (finalize does not require it). Dropped in v3 (§3.5 mechanism).
- R12 Credit note (`credit-note/route.ts`): allowed from `FINALIZED, SENT, PAID, PARTIALLY_PAID` (error text says "finalized invoices", L64-69); number = `${original.invoiceNumber}${suffix}` with suffix `b` for the first, then `max(existing).charCode + 1` (`c`, `d`, …; unbounded past `z`, L71-79); `documentType = 'CREDIT_NOTE'`, `relatedInvoiceId`, `creditNoteSuffix`; `invoiceDate = dueDate = now`; `status = 'FINALIZED'` immediately (never draft); partner, consultant, project, references, currency, language copied; invoice-level discount dropped; `notes` default `Credit note for invoice {n}`; lines = all original lines (or the subset named by `originalLineId`) with description `Credit: {original}`, `quantity = creditQuantity ?? original`, discount scaled by `creditQuantity / original.quantity`, VAT at the original line rate; **amounts are stored positive** and only printed with a `-` prefix; `creditAmount` in the body is accepted and ignored; no base-currency amounts are written (rate `null`). The UI only ever posts `{}` → full credit, after the confirm "This will create a credit note for the full amount of invoice {n}. The credit note will be immediately finalized."
- R13 The original invoice is not changed by a credit note; its detail shows `totalCredited = Σ creditNotes.totalAmount` and `remainingAmount = max(0, total − Σ payments)` — the credit does **not** reduce `remainingAmount` (`[id]/route.ts` L104-130). The list shows `_count.creditNotes`.
- R14 Payments: an `InvoiceV2Payment` row per (invoice, bank transaction) with `allocatedAmount` (`@@unique([invoiceId, bankTransactionId])`), created by the bank reconcile flow (`reconcileToInvoice`), never by the invoice routes (`InvoiceV2PaymentCreateSchema` has no caller). Rules: Σ allocations may not exceed `totalAmount` (`Total payments (x) would exceed invoice amount (y)`); status after allocation = `PAID` if Σ ≥ total **or** total − Σ ≤ tolerance (CHF/EUR/USD 0.05, SEK 0.50; `paidAmount` then recorded as the full total and a note `Rounding adjustment: CHF 0.04 (Swiss 5-cent rounding tolerance)` appended to the payment), `PARTIALLY_PAID` if 0 < Σ < total − tolerance, else unchanged; `paidDate = now` when it becomes `PAID`. `totalPaid` / `remainingAmount` on list and detail are computed from the rows, the stored `status`/`paidAmount` are a cache written at the same time.
- R15 Duplicate (`duplicate/route.ts`): copies header, references, currency, language, notes, lines (dates and period cleared) into a new `DRAFT` with `internalNotes = Duplicated from {n}` and `sourceInvoiceId`; **broken**: it calls `generateInvoiceNumber(user.tenantId, partner.code)` with the arguments swapped (L40-43) so it always throws `Partner not found…`.
- R16 Templates (`templates/*`): an invoice row with `isTemplate = true`, `templateName` (unique per tenant: `A template named "X" already exists`), `invoiceNumber = TEMPLATE-{Date.now()}`, status `DRAFT`, `partnerId` optional; CRUD only — no route or screen creates an invoice *from* a template (`sourceTemplateId` is never written) and the list route does not exclude templates unless `?isTemplate=false` is passed (the list page never passes it), so templates appear in the invoice list. Abandoned direction; dropped in v3.
- R17 List (`GET /api/invoices`): filters `partnerId, projectId, consultantId, status, documentType, fromDate, toDate (inclusive, 23:59:59.999), search (number | partner name | notes, contains), isTemplate`; sort `invoiceDate | dueDate | invoiceNumber | totalAmount | createdAt` default `createdAt desc`; page/limit (max 100, default 20); role scoping: `USER` sees own `createdById` only, `ADMIN`/`ACCOUNTANT` all (`lib/auth/data-scoping.ts` L64-81). Each row carries `totalPaid`, `remainingAmount`, base-currency total and rate.
- R18 Events logged (`EventLog`): `INVOICE_V2_CREATED, _UPDATED, _DELETED, _STATUS_CHANGED (previousStatus, newStatus), _APPROVED, _APPROVAL_REVOKED, _CREDIT_NOTE_CREATED (creditAmount, originalInvoiceNumber), _DUPLICATED`.
- R19 Quote → invoice: **does not exist in v1**. There is no quote model, numbering, template or conversion. The only artefact is the uploaded-document type `QUOTE` on a project (see Sources). v3 builds it from the decision (§3.5 keeps "quotes → invoices"; numbering: `{short}{yy}-QT-nnn`, D21/D22).

### H2 — component, preview, PDF, strings
- R20 v1 had **three renderings** of the invoice: (a) the HTML string template `generateInvoiceV2HTML` used for the PDF (`invoice-template.ts`), (b) a server HTML preview with its **own** template and the **older** translation file (`preview/route.ts` L261-503, `invoice-translations.ts`), fetched by the editor's right pane with a 300 ms debounce (`InvoiceV2Preview.tsx` L70-76), and (c) a React fallback preview (`renderLocalPreview`) used when the fetch has not returned. (a) and (b) differ (period line placement, "Project:" line, `Net` row, Intl vs apostrophe formatting, no HTML escaping in (b)). The editor form itself (`InvoiceV2Document.tsx`) is a fourth layout that mimics the PDF's section order with inputs. D7's "one component, edit / print modes" is the direct answer.
- R21 PDF layout, top to bottom (`invoice-template.ts` L431-659): centred logo (`max 200×80 px`, base64 inlined from blob, PNG assumed when MIME unknown) → right-aligned header `{title} {number}` (title `Invoice` / `Credit Note`; credit note title red `#dc2626` bold) → address block in two columns: left company (`name / address / postal city / country`), right client (`name / address / address2 / postal city / country`) → meta row: left `email`, `Org.nr: …`, `VAT: {chVatNumber if currency === 'CHF' else seVatNumber}`, `Consultant: …`; right `Date:`, `Due Date:`, `Period:` (if set), `{contractNumberLabel}:`, `{vendorIdLabel}:`, `{purchaseOrderLabel}:` (each only when value and label present), `Status: DRAFT` (only while draft) → line table `Description | Qty (centred) | Unit Price | VAT % (conditional) | Amount` → totals block (right, 300 px): `Subtotal`, `Discount` (red, `-amount`, only if > 0), VAT rows, `Total` (grey band; red band for credit notes) → `Notes: …` (if any) → `Payment` box: `{paymentTerms} Please reference invoice number **{n}**.` then `Bank Details:` table `Bank / Account Holder / IBAN / BIC/SWIFT`. Column widths with VAT column `40/12/15/10/23 %`, without `45/15/17/23 %`.
- R22 VAT column rule (L128-130): hidden when every line's `vatRate === partner.defaultVatRate ?? 0`; shown when any line differs or when there are no lines. VAT total rows (L599-625): rates with `rate > 0 && vatAmount > 0.001` only; one rate → `VAT (8.1%)`; several → one row per rate `VAT 8.1%` ascending; zero rates → no VAT row at all (the editor shows `VAT —`). `formatVatPercent`: integer rates without decimals (`25%`), otherwise one decimal (`8.1%`).
- R23 Amount column prints the line **net** (excl. VAT, after line discount); unit price prints with **0 decimals** (`CHF 1'200`); quantity prints `formatNumber(q, q % 1 === 0 ? 0 : 1)` + unit label with singular only for exactly 1 (`20 Days`, `0.5 Days`, `1 Day`); `FIXED` prints an empty quantity cell. Credit notes prefix every amount with `-`.
- R24 Payment terms text = `invoice.paymentTerms || settings.defaultPaymentTermsText || t.paymentTermsDefault.replace('{days}', settings.defaultPaymentTermsDays)` (L133-136), i.e. a free-text override per invoice, else the tenant text, else the dictionary sentence `Payment due within {days} business days from invoice date.`
- R25 Bank details on the PDF are chosen by **currency**: `CHF → ibanCHF`, anything else → `ibanSEK` (L653-654; an EUR invoice gets the SEK IBAN); `pdf/route.ts` L185-204 lets a partner's `receivingBankAccount` override bank name, BIC and the IBAN of the matching currency. The VAT number printed follows the same currency switch (R21), not a registration.
- R26 Languages: `en, sv, fr, de` dictionaries with English fallback (`getInvoiceV2Translations`, L267-272); locale for dates `en → en-GB, fr → fr-CH, sv → sv-SE, de → de-CH` (L277-286); dates `toLocaleDateString(locale, {day:'2-digit', month:'long', year:'numeric'})` → `31 January 2026` / `31 janvier 2026`. Money in the PDF is **not** locale-aware: `formatCurrency` = `{CUR} {n with ' thousands and . decimals}` → `CHF 25'944.00` in every language (`formatting.ts` L11-43). The React preview used `Intl.NumberFormat(locale, {style:'currency'})` instead (`CHF 25,944.00` / `25 944,00 CHF`). The language is a per-invoice field; `Partner.language` (default `en`, L369) exists but the V2 form never reads it — the form default is `en` and the user picks in the header select. v3: default from `partner.defaultLanguage`.
- R27 PDF generation (`generator.ts`): puppeteer, `page.setContent(html, {waitUntil:'networkidle0'})`, `format A4`, `printBackground true`, margins `top 20mm, right 15mm, bottom 25mm, left 15mm`, empty header, footer template `8px #999 centred, top border` with `{companyName} • {email} • {website}` on every page. `settings.invoiceFooterText` is shown in the editor and React preview but never in the PDF. No page-break rules; long invoices just flow.
- R28 `GET /api/invoices/[id]/pdf` renders on every call, uploads the PDF **once** per invoice to blob `invoices/Invoice_{n}.pdf` and creates a `Document` of type `CLIENT_INVOICE`, source `INVOICE_GENERATION`, linked `GENERATED` to `INVOICE_V2` (L231-284); later calls re-render but reuse the document; download name `Invoice_{n}.pdf` / `CreditNote_{n}.pdf`. ### H6 — Swiss VAT return
- R31 Period = calendar quarter; `getQuarterDates(year, q)` → local-time `[1st of month 3(q−1), last day of month 3q]`; `year ∈ [2020, currentYear + 1]`, `quarter ∈ 1..4` (errors in `fixtures/swiss-vat-cases.json`). Warnings `future_period` (start > today) and `incomplete_period` (end > today) are informational.
- R32 Membership of an invoice in a period is **computed, never stored**: `invoiceDate` within the quarter AND `status ∈ {SENT, PARTIALLY_PAID, PAID}` AND `currency = 'CHF'`, on the old `Invoice` table (R1). The owner's Excel instead carries a typed column `VAT Declaration = CH 2026/Q2` per invoice (excel-to-v3 sheet 2). `FINALIZED` invoices are excluded until marked sent; a Swiss client billed in EUR/SEK is excluded by currency.
- R33 Swiss client test: `isSwissCountry(partner.country)` true for `ch, switzerland, suisse, schweiz` (trimmed, case-insensitive) **and for null/empty** ("conservative default"). Swiss → refs 303/313/343 by line rate (`|rate − 8.1| < 0.01` etc.; any other rate > 0 falls into 303 at 8.1 %, so a 7.7 % line would be taxed at 8.1 %); non-Swiss → ref 221 "services abroad" (no VAT, place of supply abroad) — v1's only notion of "reverse charge" on sales. Line rate comes from `line.vatCode.rate`, so an old-model line without a VAT code counts as 0 %.
- R34 Credit notes: an invoice with **negative** `subtotal` goes to ref 235 (reductions) and is otherwise ignored; its base is **not** removed from 303, so 379 ≠ 299 and the plausibility warning fires (fixture V4). V2 credit notes (positive amounts) are invisible to the report (R1).
- R35 Input VAT (ref 400): supplier-invoice lines of the period with `status ∈ {APPROVED, PAID}` and `vatCode.country = 'Switzerland'` → `net × rate/100`; expense claims of the period with `status ∈ {APPROVED, REIMBURSED}` and a Swiss `vatCode` on the header → VAT extracted from the gross `gross × rate / (100 + rate)`. Refs 405/410/415/420 manual; 383 (acquisition tax) always 0; 205/230 always 0; 220/225/280/900/910 manual.
- R36 Rates: `SWISS_VAT_RATES = {STANDARD 8.1, REDUCED 2.6, ACCOMMODATION 3.8}` (2024+). Seeded codes `CH81, CH26, CH38` (+ `SE25, SE12, SE6, SE0 "Export/reverse charge"`); the schema comment still lists `CH77` (7.7 %, until 2023-12-31) but nothing seeds or maps it.
- R37 Output: every ref rounded to 2 dp; UI with copy-to-clipboard per value, drill-down of contributing invoices (`SwissVatInvoiceDetail`: number, client, country, date, net, vat, vatCode of the first line, rate, isSwissClient) and input sources; CSV export `swiss-vat-{year}-Q{q}.csv`, `;`-separated `ref;label;amount` (labels in `fixtures/swiss-vat-form-fields.json`); a `VatReturn`/`VatReturnLine` model exists (return number `VAT-SE-2025-Q1`, status `DRAFT, SUBMITTED, PAID, LATE`) but the Swiss page never writes it — nothing records that a quarter was declared or paid.

## 4. Algorithms / formulas

### H1 — totals (`calculateLineTotals`, `calculateInvoiceTotals`), rounding `round2(x) = Math.round(x × 100) / 100` (floats in v1; Decimal in v3)
Per line:
1. `gross = quantity × unit_price`
2. `discount = gross × discount_percent / 100` (PERCENTAGE) | `discount_fixed` (FIXED) | 0
3. `net = gross − discount`; `vat = net × vat_rate / 100`; `total = net + vat`; each of the five rounded to 2 dp when stored.
Per invoice:
4. `subtotal = Σ line.net` (rounded line values)
5. `discount_amount = subtotal × discount_percent / 100` — **PERCENTAGE only**; `FIXED` at invoice level is accepted by the schema and silently ignored (fixture L)
6. `net = subtotal − discount_amount`; `ratio = subtotal > 0 ? net / subtotal : 1`
7. `vat = Σ line.vat × ratio`; `vat_breakdown[rate] = Σ line.vat × ratio` filtered `amount > 0`, sorted by rate ascending
8. `total = net + vat`; all rounded to 2 dp at the end.
Worked cases A–L in `fixtures/invoice-totals-cases.json`. Property for v3: `total == net + Σ breakdown` and `subtotal == Σ line.net` after rounding; `|Σ line.total − total| ≤ 0.01 × lines` is **not** guaranteed by v1 (line totals are rounded separately) — v3 should print line nets and compute VAT once per rate on the summed base (what the FTA and the accountant expect), then `total = net + Σ vat_by_rate`. Negative lines via FIXED discount > gross are accepted by v1 (fixture K) — reject in v3. No 5-cent rounding anywhere (`roundTo5Cents` exists, tested, unused).

### H1 — numbering (what survives: the format)
v1 (260 lines): lazy `(tenant, partner, year)` row, serializable transaction, 5 retries, number consumed at preview time, year = today. v3: `nextInSeries(tx, caller, invoiceSeries(partner.short_code, issue_date))` inside the issuing transaction (`specs/numbering/spec.md` R1), formatted `formatSeriesNumber(series, n)` → `VA26-001`; `peekSeries` for the "next number will be" hint on the draft; credit notes `VA26-CN-001`, quotes `VA26-QT-001` (D21). Year from the **issue date**, not the clock. No retry loop (row lock queues writers), no reset, no settings.

### H1 — credit note amounts (v1, `credit-note/route.ts` L94-131)
For each credited line: `qty = creditQuantity ?? original.quantity`; `gross = qty × unit_price`; `discount = original.discount_amount × qty / original.quantity`; `net = gross − discount`; `vat = net × original.vat_rate / 100`; header `subtotal = Σ net`, `vat = Σ vat`, `total = subtotal + vat`, no invoice discount, unrounded floats. v3: same proportional rule through the §4 totals function, Decimal, and `Σ credited ≤ original` enforced across all credit notes of one invoice.

### H1 — due date (`calculateDueDate`): fixture `format-cases.json#dueDate`. v3 keeps calendar vs business days as a property of `contract.payment_terms` (`"30 days"` / `"30 business days"`), no holidays.

### H1 — paid status (`determinePaymentStatus`): `fixtures/payment-tolerance.json`. v3 derives it from `link` allocations with the linking module's tolerance (bank fees are larger than 0.05 — H3 decides the rule; the rounding note moves to the link).

### H2 — formatting per locale
`fixtures/format-cases.json`. v3 rule (skill: "formatted with the partner's locale", Decimal until the formatter): one `formatMoney(amount, currency, locale)` in `kernel/money` display helpers — decide between v1's PDF style (`CHF 25'944.00`, Swiss convention, language-independent) and Intl per language (`25 944,00 CHF` for sv). The owner's Excel and his Swiss client read the apostrophe style; recommendation: apostrophe thousands and `.` decimals for `fr`/`en`, Intl `sv-SE` for `sv` (**Q3**). Dates: `dd MMMM yyyy` in the invoice language (`31 janvier 2026`). VAT %: integer without decimals, else one decimal. Quantities: up to 1 decimal, unit label singular for exactly 1.

### H6 — the return (per quarter, per CH registration; v1's rules consolidated on the one model, the credit-note and rate-by-date lines are the v3 corrections of R33/R34)

# Banking — Nordea import, transactions, categorisation rules, transfer pairs

Module `src/modules/banking` · schema `prisma/schema/banking.prisma` · migrations `20261021100000_add_banking_import_and_journal`, `20261027120000_one_transaction_table`, `20261027200000_owner_private_role` + `20261027200100_link_payment_record` (F114), `20261104120000_justified_partner` (F129: the four partners, the backfill — on `partners`) · specs `specs/banking/` (harvest, spec, plan, tasks), `specs/banking/one-table.md` (F113; PR C built by F129) and `specs/linking/payment-record.md` (F114, the payers), `specs/justify/rework.md` (F129), [[review-2026-10-31]] §6.1 (F128, the import preview) · decisions D3, D13, D18, D25, D31, D58, D59, D60, D73, D74. Part 1: model, parser edits, import, rules, transfer pairs, linkables, queries. Part 2: the workbench, the imports and rules pages. Since F113 (2026-10-27) the row carries its own facts — the [[journal]] module is gone.

> A bank transaction is one CSV row, kept verbatim: the bank's columns and the SEK base (rate, source, date — written once by the import) are locked by the database; the owner's facts about it — BAS category, partner, note, *no document needed* — are on the same row and change freely (F113, D59). **A justified row names a partner** (F129, D73): *open / partially linked / linked / linked · no partner / no document needed / no proof · no partner* are **derived** from the links, the row's flag and its **effective** partner — typed, else the proof's (D58, derived on read, never written). Rules set facts, never a status; transfer pairs are `transfer` links — and only links: accepting one writes nothing on the legs (F65).

## Model

```

                      owner_private (F114, D60) = the owner's private instruments (`Private SE`, `Private CH`): no CSV format (bank_format_id is
                      NULL only for them — a CHECK), no rows, never imported into; what a private expense names as its payer
                      UNIQUE (tenant_id, id) — the composite key `expenses.paid_from_account_id` / `subscriptions.paid_from_account_id` point at (D63)
bank_imports          account · file_name · document_id (the stored CSV, validated UUID) · record/imported/duplicate/error counts
                      errors [] · period_from / period_to (min/max booking date) · imported_at

                      sender · recipient · name · additional_details · message · own_notes   (the six raw columns, verbatim)
                      description · reference · counterparty_key · dedup_hash · occurrence · row_index
                      amount_base (SEK, 2 dp, signed like amount) · rate (6 dp) · rate_source ∈ same_currency | ecb_daily | ecb_nearest (the shared enum; `bank` refused by a CHECK) · rate_date?
                      bas_code? · partner_id? (composite FK to partners, RESTRICT — D63) · note? · no_document_needed · categorised_by ∈ manual | rule | null · rule_id?
                      UNIQUE (account, dedup_hash, occurrence) · trigger bank_transactions_lock_facts (the bank's columns and the base refuse an UPDATE; the owner's facts pass)

                      match_field ∈ counterparty_key (default)|name|details|message|sender|recipient|all
```

Cross-module references: `partner_id` is a composite `(tenant_id, id)` FK to `partners` (RESTRICT, D63 — the first one); `document_id` and `rule_id` stay validated UUIDs until their modules' next schema PR. `bank_transactions.bank_account_id / bank_import_id` are intra-module FKs (RESTRICT / CASCADE).

`journal_entries` still exists in the database after F113's migration, read by nothing — PR B drops it after one real month on the box — a safety wait before dropping data, kept though D65 was lifted ([[roadmap]]).

## The parser — `csv-parser.ts` (v2, three D25 edits)

Buffer + format config → rows. (1) The header row is validated against the format's labels **or their aliases** (`Date` for `Booking date` — the owner's real exports say `Date`); anything else is *Not a Nordea export*. (2) A space thousands separator (`-1 500,00`) is accepted. (3) The dedup hash is `sha256(date | amount | currency | sender | recipient | name | additional details | message)` — never the row's position, the balance (end-of-day only) or the owner's notes (editable in Nordea); identical rows of one file get `occurrence` 0, 1, … Dates are checked as calendar dates; a bad row is reported (`Row 7: invalid amount "abc"`) with the others parsed around it — and **the import refuses the whole file** when any row failed (F109, audit 2026-10-27 B5): *2 rows could not be read — Row 2: …; Row 3: … — nothing was imported* (`VALIDATION_ERROR`, `details.errors` one per line). Proof-per-transaction books cannot afford a silently missing row; the owner fixes the export or the format once. The old formula-injection flag (`+`, `-`, `=`, `@` as a first character) is gone — nothing here is a spreadsheet, and it padded `errorCount` with noise. `bank_imports.error_count` / `errors` are therefore always 0 / `[]` from now on (kept for the history).

Derived text: `description` = name → additional details → sender → recipient → *Unknown transaction*; `reference` = the `Message` column verbatim; `counterparty_key` (`counterparty.ts`, Excel *Column1*) = name, else the details without the card prefix (`Kortköp 260727 OPENAI *CHATGPT SUBS` → `OPENAI *CHATGPT SUBS`), else message / sender / recipient; upper-cased, trailing 4-digit card suffix dropped, whitespace collapsed, and — D71 (F124 (6), 2026-10-30) — **a per-transaction reference at the end dropped** (`stripReference`: a trailing `#…` bill number, a trailing `* CODE` whose code carries a digit — `MICROSOFT#G169504312` → `MICROSOFT`, `MSFT * E0100ZW7M8` → `MSFT`; `OPENAI *CHATGPT SUBS` keeps its product name). A key is a *who*, never a *which*: with the reference kept, next month's row of the same merchant was a different key, so rules from a row, the counterparty memory and the history never recurred for card purchases. The migration `20261030010000_counterparty_key_without_reference` applied the same two expressions to the stored keys and to the `contains` / `exact` patterns of the rules on the key (the lock trigger stepped around for that one statement); `counterparty-key-migration.test.ts` replays it on a scratch database and holds the SQL and the TypeScript equal.

`account-detect.ts`: the filename pre-selects the account (`PLUSGIROKONTO FTG 123 45 67-8 - …` → the number; the first row's currency picks between the SEK and CHF main accounts that share it). A hint for the dialog, never a creation.

## The import — `import.ts`

`importCsv(tx, caller, audit, storage, {bankAccountId, fileName, bytes})`, one transaction, nothing written before every check passed:

1. parse (header, rows, per-row errors) · 2. every row's currency = the account's, else *Currency CHF in file does not match account Plusgirokonto SEK (SEK)* · 3. dedup per account on `(hash, occurrence)` (`planImport`) · 4. a base rate is resolved for every new booking date (`facts.resolveRate`: SEK → rate 1 `same_currency`; CHF → ECB of the booking date, nearest weekday; *No exchange rate for 2026-07-08 — run the ECB sync*) · 5. the CSV stored as a document (`documents.storeGeneratedDocument`, `text/csv`, `bank_statement`, status `generated`, key `Bank_Plusgirokonto-SEK_2026-07-03_2026-07-28.csv` from `numbering.bankStatementKey` — even when every row was a duplicate: the package needs the file) · 6. the import record · 7. the transactions in file order, each with its base (`amount_base = round(amount × rate, 2)`, audited) · 8. the active rules on the new rows (the two defaults are created first when the tenant has none — `ensureDefaultRules`).

A failure after the first write is **thrown** as `RollbackError` (kernel/errors) so the transaction rolls back whole; the action client returns its `appError` like a returned error. (A returned `ServiceResult` error would commit the partial write — the middleware commits whatever the handler returns.)

Steps 1–4 are one read, `parseForAccount(tx, input)` → `ParsedFile` (the account with its format, every row, the fresh ones and the duplicate count, the period, a base rate per new date) — the import writes from it, the preview below shows it; the refusals are the same function's, so the dialog shows before *Import* exactly what the import would refuse.

### The preview — `import-preview.ts` (F128, [[review-2026-10-31]] §6.1)

```
file ─► detectAccountAction (the account proposed) ─► previewImportAction (a read, owner) ─► the table ─► [Cancel] [Import N] ─► importCsvAction (all-or-nothing, F109) ─► the summary
                                                          │
                                                          ├─ parseForAccount        → every row · new / duplicate (planImport) · the period · the import's refusals (F109)
                                                          ├─ the rules, dry run     → firstHit over orderRules(active rules) on the new rows, as applyToTransactions writes them
                                                          ├─ balanceChain           → the account's rows + the new ones: complete to <date>, the gaps (F115)
                                                          └─ linking (at call time) → an incoming row's text tokens (referenceTokens) ∩ the open issued invoices' numbers → scoreMatch
```

`previewImport(tx, caller, { bankAccountId, fileName, bytes })` → `ImportPreview`: the header (`recordCount` · `periodFrom → periodTo` · `completeTo` / `balanceGaps` · `duplicateCount` · `willImport` = the rows *Import* writes), the rows in file order with their **Will be** (`willBe`, derived by `previewVerdict` — one place) and the facts behind it, `ruleHits`, `invoicesFound`. **Nothing is written**: no row, no import record, no document, no rule, no partner (`import.test.ts` holds the counts still). The words:

| *Will be* | Means | After *Import* |
|---|---|---|
| `new` | not in the account yet; no rule, no invoice known | an *open* row — the owner justifies it |
| `duplicate — already imported` | its `(hash, occurrence)` is in the account (D25) — greyed | skipped; not re-judged (no rule, no invoice on it) |
| `no proof needed · <rule> · <partner>` | the first active rule to hit sets *no document needed*; its partner (D73 — `· no partner` when the rule has none: the row will sit under *Needs a look*) | the rule writes the flag, the category and the partner — *no document needed* |
| `<code · label> · <rule> · <partner>` | the first rule to hit sets a category (the rule's, else its partner's default — what `applyToTransactions` writes) and / or a partner | the rule writes them; the row still needs its proof |
| `pays invoice <number> (proposed)` | incoming row: an **open issued invoice** in the row's currency whose number is a token of the row's text (`referenceTokens` — the scorer's 40-point reference claim); two numbers in one text → the better-ranked one; `confidence` is `scoreMatch`'s on the parsed row's facts (the same facts the row's linkable gives once imported) | **nothing stored for it**: the row's *Suggestions* finds the same invoice again (HIGH when the amount agrees), `Enter` / *Link* writes the link — a link on a click only (D60) |

The rules of a tenant that has none yet are the two defaults `ensureDefaultRules` will create on this import (the bank named after the account's format, or the bank partner when it exists — F129). Linking is read with `await import("@/modules/linking")` inside the invoice step: `banking.actions → linking → linkables → banking` is the load cycle ([[lessons]] *F113 build*); the candidates come from the invoice linkable's own `references` lookup, what is open on them from `linking.allocatedSums`. The preview checks the base rates too (step 4): *No exchange rate for … — run the ECB sync* shows before anything would be written. `previewImportAction` (owner, the same FormData as `importCsvAction`) hands it to the dialog; `importCsvAction` is unchanged.

`deleteImport`: refused when any of its transactions is linked (`linking.linksTouching` + the delete trigger); else the transactions and the record go, audited. `deleteBankAccount` refuses while imports exist.

## Rules — `rules.ts`

Pure: `orderRules` (active, priority desc → longer pattern → newest), `fieldText` (`all` = the five text columns joined), `matchRule` (case-insensitive; an invalid regex never matches, never throws), `firstHit`. Fixture `specs/banking/fixtures/categorisation-rules-sample.json#testPatternCases` runs in `rules.pure.test.ts`.

Service: `createRule` / `updateRule` / `deleteRule` (name pre-checked — a unique violation would abort the Postgres transaction; BAS code through `settings.getBasCategory`, partner through `partners.getPartner`, regex compiled on save), `testRule` (matches / tested over the newest 500 uncategorised rows), `applyRules({dryRun})` (every active rule over every uncategorised row — `facts.uncategorisedTransactions`; dry run previews ≤ 50 and writes nothing), `applyToTransactions` (the import's call; a rule's `hitCount` / `lastHitAt` count only the hits that changed the row — a match the never-overwrite rules turn into a no-op is not a hit, lessons audit 32), `createRuleFromTransaction` (pre-filled from the counterparty key and the row's facts, `learned`, applied to that row at once), `ensureDefaultRules` (`AVGIFTER NORDEA` → 657 no document; `^(R[äa]nta|Interest)\b` on the details → 831 no document — both name **the bank** since F129: `DEFAULT_RULES` carry `partnerRole: "bank"`, resolved through `partners.systemPartner` when they are made; `importCsv` calls `partners.ensureSystemPartners` — the bank named after the account's format, Skatteverket, the Swiss FTA, the owner as employee, once per tenant — just before). `rulesForKey(tx, key)` (F129 FR-008, D74): the active rules whose text matches a counterparty key alone, in run order — what `justifyRow`'s rule proposal and F130's vendor check read; text only, the account / sign / amount conditions are the import's business.

A hit writes through `facts.categorise(…, {by: "rule", ruleId})`: category when the row has none (a partner-only rule brings the partner's default category), partner when none, the flag OR-ed; a row categorised **by hand is never touched**. Counters (`hit_count`, `last_hit_at`) move on real applies.

**Conditions beyond the text** (F116 PR C1, `specs/linking/one-engine.md` FR-007, D67; migration `20261028090000_rule_conditions`): a rule may also name the **paying account** (`bank_account_id`, composite FK, a statement account only — a private instrument has no rows), the **direction** (`sign` ∈ any · in · out), an **expected |amount|** with a **tolerance %** (`expected_amount`, `tolerance_pct`, default 0.5) and a **cadence** (none · monthly · quarterly · yearly). `conditionMiss(rule, text)` (pure) names the first condition a row fails — a fact the caller does not know is not checked, so every existing rule matches as before; `firstHit` = text ∧ conditions; `firstNearMiss` = the rule whose text matched when none hit. **The cadence flags, it never blocks** (as built — a year file of interest rows would otherwise leave eleven of twelve uncategorised): `offCadence(cadence, rows)` marks the later row of every gap outside `CADENCE_DAYS` (monthly 20–40 days, quarterly 75–105, yearly 330–400). `ruleNearMisses(tx)` → the rules page's **Needs a look** (`RuleNearMisses`): uncategorised rows a rule almost categorised, with why (*another account* · *the other direction* · *expects 132.52 ± 0.50 %*), rows categorised off their rhythm — each opens its row on the workbench — and, since F129 (FR-009), **an active rule that sets *no proof* without a partner** (`reason: no_partner`, `transactionId: null`, `rows` = how many rows carry its `rule_id`), after the row entries, with *Edit rule* (the `RuleDialog` in place; the page hands the component the rules): its rows stay *no proof · no partner* until the rule names one. The rule dialog's *Only when…* fieldset edits the four (`ruleAccountOptions` — the statement accounts); *Create rule from this* pre-fills the row's account and direction and leaves the amount open (a price change is not a new counterparty).

## The row's facts — `facts.ts` (F113; the journal's service, on the row)

`baseAmount(amount, rate)` (round half-up, 2 dp, never `-0`) · `resolveRate(tx, date, currency)` / `baseFor` (the base rule above, through [[rates]] `rateToBase`) · `categoriseSchema` + `categorise(tx, caller, audit, id, {basCode?, partnerId?, note?, noDocumentNeeded?}, {by?, ruleId?})` — by hand: what is given is written, `categorised_by = manual`, `rule_id` cleared; by a rule: the never-overwrite rules above; the audit row holds the owner's facts only (`ownerFacts`), so the History diffs them · `transactionFacts(tx, ids)` → `Map<id, BankTransactionDto>` (what expenses, supplier invoices and the package read for the row's base) · `uncategorisedTransactions(tx, limit)`. The BAS code is checked through [[bas-categories]] (`settings.getBasCategory`), the partner through [[partners]]. `facts.ts` never reads the links: `banking.actions` reads `categoriseSchema` at load time and linking's registry loads every module, so a static edge from here to linking would close the load cycle the journal hid behind `await import` ([[lessons]]) — the implied rate of a transfer pair is `implicit-rate.ts` (`impliedRate`, `withImplicitRates`), read by `queries.ts` only.

## Transfer pairs — `transfer-pairs.ts`

Pure `transferCandidates(a, others, ecbRates)`: another own account, opposite sign, ≤ 2 days apart; same currency → equal amounts (rate 1); else `implied = |SEK| ÷ |foreign|` within 5 % of the ECB rate of `a`'s date **for that pair's foreign currency** (`ecbRates`: currency → SEK per unit; `proposeTransfers` fetches one rate per foreign currency among the legs — a SEK row meeting a CHF and a EUR candidate compares each with its own rate, lessons 32). Hints (`CHANGE`, `CHFSEK`, `ÖVERFÖRING`, the other account's number in the text) raise the confidence shown, never required. Constants, not settings.

`proposeTransfers(tx, id)` (empty once paired) · `acceptTransfer(tx, caller, audit, {fromId, toId})` → one `transfer` link debit → credit (through [[linking]]); the foreign leg's implied rate is derived from that link on read (`implicit-rate.ts` `withImplicitRates` — nothing stored, F86) and its `rate` / `amount_base` stay ECB, D3. **Nothing else is written on the legs** (F65, D44): no `no_document_needed`, no `categorised_by = manual` — so rules still categorise an accepted leg, and unpairing (removing the link) leaves both rows exactly as before. The state *no document needed* of a leg is derived from the link. Unpairing takes the implied rate away with the link; a re-pair shows the new pair's. The owner's July pair: −20 000.00 CHF ↔ +237 740.00 SEK → 11.887 (fixtures `nordea-transfer-pair-*.csv`).

## The effective partner and category — `effective.ts` (F129, D73 (a) = D58, one-table PR C)

```
rowFacts(tx, rows)  ─ linksTouching once ─► linkFactsOf (Σ allocated, the transfer legs)
                    ─ the allocating links FROM the rows, in creation order ─► one factsMany per target type (linking's registry)
                    ─ partners.systemPartner(owner) once (a `settles` link pays him back)
                    ─► effectiveFactsOf(row, proofs, ownerId) per row  →  { partnerId, partnerFrom, basCode, basFrom, mixed }
```

`effectiveFactsOf` (pure, client-safe): a **typed** value wins (`from = row`); else the proof's (`from = proof`) — the first non-null value of the proofs ordered by `allocated_base`, largest first, ties in the links' order; `mixed` when the proofs name more than one partner or account among them. A `justifies` onto an expense or a supplier invoice brings its partner and `bas_code` (`EntityFacts.basCode`, F129 FR-004); onto an invoice its client; onto a plain document nothing (example 9 of the spec: *linked · no partner* until the owner picks one). A `settles` link's partner is the owner as employee (the seeded `owner` partner), its category the expense's. **Nothing is written**: `SELECT partner_id, bas_code` stay as typed, the History holds no categorisation (`reads.test.ts` holds the audit count still across a link and an unlink). Every reader goes through `rowFacts`: `loadRows` (the list), `getTransaction` (the panel — `TransactionDetail.effective` with the partner's name and the BAS label; the *Category* section prints them with *from the proof* above the form that edits the typed value), `transactionStates` (the package, `outgoingRowsInWindow`), `bankMonths`, `rowsToJustifyCount`, `proposalRowIds` / `proposalInputs` (a row whose category or partner is derived lacks nothing — no proposal, F98) and `currentForRows`' row facts.

## Derived state and lists — `queries.ts`

`deriveTransactionState({amount, allocated, inTransfer, noDocumentNeeded, partnerId, accountRole})` — **the one place** (F129 FR-006): a transfer leg is `no_document` (the other statement row is its proof — F65); a flagged row is `no_document` with a partner (typed or effective) and `no_document_no_partner` without one — unless it sits on a **savings** account, whose statement is the proof (Q3; `NO_PARTNER_ROLES`); else `linked` / `linked_no_partner` when `Σ allocations ≥ |amount| − tolerance` (the kernel's `isSettled`, D25); `partial` when Σ > 0; else `open`. Never stored. `needsProof` (`months.ts`) = `open | partial | linked_no_partner | no_document_no_partner` — what the Months panel, the sidebar's count, the inbox and the package call *to justify*; `state-family.ts` shows the two new states as *attention* (*Linked · no partner*, *No proof · no partner*). The link facts come through [[linking]]'s read API — `linkFactsOf(links, rows)` (`link-facts.ts`, pure, F114): Σ allocated FROM the row **in the row's currency** over the allocating kinds (`justifies` / `settles`), a cross-currency link counting by the share of the row's base it took (`allocated_base` over the row's base — linking's `rowRemaining`, the one rule the list, the Months panel, the sidebar's count and the package share), and the transfer legs; the links by `linksTouching` — banking reads no `links` table itself (lessons audit 22).

`TRANSACTION_COLUMNS` is the DataTable contract; the list runs in two steps (Prisma on the stored columns — the base and the owner's facts are columns now, F113 → `rowFacts` (Σ allocations, the effective partner and category), the implied rates, partner names and BAS labels joined over that set → derived filters, search, sort, page and sums in memory through `kernel/list-query/memory`, cap 20 000). Since F129 `partnerId` · `partnerName` · `basCode` · `basLabel` are the **effective** values and join `DERIVED` (the Partner header filter and its distinct values run on them, like *State*); `partnerFrom` / `basFrom` (`row` · `proof`) and `mixed` are hidden columns; the category cell carries a grey *mixed* tag when the proofs disagree. `distinctTransactionValues` / `transactionDateHierarchy` keep Excel semantics. `getTransaction` returns the row with its facts and implied rate, the state, the links with the other side's label and the transfer proposals. `getTransactionAction` hands it to the panel as `TransactionDetailWire` (`detail-wire.ts`: the timestamps as ISO strings), the type the panel reads — no cast on the client (lessons 29). `listImports`, `listRulesWithLabels`, `accountBalances` (the balance of the latest booking date that has one — no stored running balance). Since F71 the imports and rules pages are DataTables too: `IMPORT_COLUMNS` / `RULE_COLUMNS` with `listImportsPage` / `listRulesPage`, `distinctImportValues` / `distinctRuleValues`, `importDateHierarchy` / `ruleDateHierarchy` — a handful of rows, so every column is evaluated in memory (`memoryTable`, the same `kernel/list-query/memory` semantics); `accountLabel` is an `enum` column (a checkbox filter of account names). `rawRowsForPeriod({from, to, by: "booking" | "import", role?})` — the raw rows of a period with their account, source file and the account's CSV conventions, booking date then file order: what the [[accountant-package]] writes as `bank-statements/*.csv`. `accountAliasesFor(tx, transactionIds)` → `Map<transactionId, accountLabel>` in one query.

## The Months panel — `months.ts` (F69)

A read model, no table: `bankMonths(tx, {today})` → per month from the first month an import covers (at least twelve months back) to today's month:

```
bank rows of the window ─┐
the row's flag (no doc) ─┼─► rowFacts ─► deriveTransactionState ─► justified  = linked | no_document   (each with a partner, F129)
links (linking index)  ──┘    (the workbench's rule)                to justify = open | partial | linked_no_partner | no_document_no_partner
imports' period_from → period_to ─► per account × month: proven (imported, nothing to justify — rows or not — AND the balance chain covers the month whole, F115)
the balance chain (accountCompleteness) ─┘           incomplete (imported, nothing to justify, the chain does not prove the month — half a month, the running month, the first export's month, after a gap)
                                                         open (≥ 1 row to justify) · not imported (no import covers it, no row)
package.builtPeriods(months) ─► banner = the newest closed month with bank rows whose monthly package is not built
```

- **Bars** — rows justified (`--state-done`) under rows to justify (`--state-attention`), scaled to the busiest month; a click on a bar sets the table's Month filter (`f.bookingDate=dates:2026-07`), a second click (or *All months*) clears it. The panel starts scrolled to today's month.
- **Squares** — one row per account (main and savings), the same states for that account only; the words are in each square's label and the legend. Each account row says *complete to <date>* and *N gap(s)* when the chain found any, or *no balance chain yet* (F115).

## Completeness by balance — `completeness.ts` (F115, audit B4, `specs/banking/completeness.md`)

The bank's running balance is the proof that no row is missing. Per account, ordered by day, `balance(d₁) + Σ amount(rows with d₁ < date ≤ d₂) = balance(d₂)` holds exactly when every row between two balanced days is here — inside one export and between two; it breaks by exactly what is missing. `balanceChain(rows)` (pure) → `{completeFrom, completeTo, gaps, balancedDays}`: a day's end-of-day balance is the one on its latest row (Nordea's first row of the day; an older export with a balance on every row takes the one that agrees), days without a balance are summed into the next balanced day; a gap is `{from, to, expected, actual, difference}` and the chain re-syncs on the bank's balance after it; `completeFrom` = the first balanced day (nothing before it is proven), `completeTo` = the last balanced day before the first gap. `monthComplete(c, month)`: `completeFrom` before the month's first day and `completeTo` on or after its last — never on half a month. `accountCompleteness(tx, accountIds?)` (queries.ts) runs it over every row of each account, one query. **The import** reports the chain after the file is in (`ImportSummary.completeTo`, `balanceGaps`, `currency`; the dialog: *Balance chain: complete to 2026-07-28* / *Gap between … and …: the balance is off by −200.00 SEK — rows missing between exports? Export those days again.*) — reported, never refused. Nothing stored: the balance is the column the import already keeps (D25).
- **Banner** — *Rows to justify: N — package YYYY-MM not built. Open package* (`InfoBanner` in the page header; the wording since F129: a linked row without a partner counts). Never the running month; gone once that month's package is built (any version). Savings rows count by booking date here, though the package takes them by import (D31).
- Read from `package/index.ts` (`builtPeriods`) and `linking/index.ts` (`linksTouching`, `ALLOCATING_KINDS`) — banking reads no other module's table for it. The panel is hidden until the first bank row.

## Accounts — `bank-accounts.ts`

CRUD on Settings → Bank accounts ([[bank-accounts]]) — the **statement accounts** (`STATEMENT_ROLES` = main | savings; `checkRole`). Once a CSV is imported into an account its **number and currency are locked** (F65): `updateBankAccount` refuses a change of either with *This account has N import(s); its number and currency can no longer change* (`BUSINESS_RULE_VIOLATION`, `details.imports`) — they say which rows belong to it. Alias, IBAN / BIC, format and role still change. `getBankAccounts` returns `BankAccountDto[]` with `imports` (the count; `bankFormatId` / `bankFormat` nullable — null only on a private instrument) and the settings tab disables the two fields when it is > 0; `getBankFormats` returns `BankFormatDto[]` — the format's conventions and its column mapping parsed (`parseColumnMapping`, null when it does not fit); neither leaks the Prisma row (lessons audit 30). Delete is refused while imports exist.

**Payers — `payers.ts` (F114, D60).** Who can pay an expense or a subscription is a bank account: `payerAccounts(tx)` → `PayerAccount[]` (id, label, currency, role, `kind` ∈ bank_account | private — `payerKindOf(role)`, a lookup, never a role comparison in a module) — the main accounts first (the company paid; a `justifies` link from the row proves it), then the owner's **private instruments** (`role = owner_private`; a `settles` link from the refund row reimburses them); savings pay nothing. `payerAccount(tx, id)` resolves one. `createPrivateAccount({alias, currency})` is the only way to make one — the alias is the number too, no format, no IBAN; `importCsv` refuses a private instrument (*has no statement*). The seed makes `Private SE` (SEK) and `Private CH` (CHF). Settings → Bank accounts shows them under **Private instruments** (`PrivateInstruments`: the list and *Add*), apart from the statement accounts. The `payment_sources` table of expenses is gone — the F114 migration turned each private source into an `owner_private` account and repointed the expenses.

## History — `history.ts` (F71)

`transactionHistory(tx, id)` reads two audit trails through `kernel/audit` `getAuditLog` and maps them (`toHistoryEvents`, pure): the row's own `create` = **Imported** and its `update`s (a categorisation, F113 — the updates written on journal entries before were appended onto the row's trail by the migration) = **Categorised 657** / *Category removed* / *Partner changed* / *Marked no document needed* / *Document needed again*, each with who decided it (rule, by hand, partner default); each live link's `create` = **Linked: Supplier invoice (justifies)** (the other end's type, the kind). An update that changes nothing the owner sees (a note) is dropped. A **removed** link is not shown: its row is gone and the kernel reads a trail by entity id only ([[lessons]], F71 banking History).

## Proposal inputs — `proposal-inputs.ts` (F98)

Banking serves what stage 1 of the proposals reads ([[linking]] *Proposals*), read only: `proposalRowIds(tx, { importId } | { transactionIds } | { all })` — the rows not categorised by hand and missing a category or a partner; `proposalInputs(tx, ids)` — each with the first active rule that would set a fact (a partner-only rule brings the partner's default), the partner's default category, and `categoryMemory` — what the owner set **by hand** on the same counterparty key's other rows, counted. `importCsvAction` enqueues `linking.propose-for-rows` once the import has committed; `deleteImport` drops the rows' proposals first (`linking.dropProposalsFor`). The list's derived `proposedBasCode` · `proposedSource` · `proposedConfidence` come from `linking.currentForRows`.

## Read API for other modules (lessons audit 23)

Expenses and supplier invoices read `bank_transactions` themselves today; these replace those reads (the callers move in their own lanes):

- `outgoingRowsInWindow(tx, { bankAccountIds, from, to })` → `WindowRow[]` (F94): outgoing rows of those accounts booked inside the window (inclusive), oldest first, *linked* / *no document* rows dropped, with every text field, the row's partner / category / flag, |base| and what is left — the subscriptions matcher's candidates.
- `outgoingMainRows(tx, limit)` → `OutgoingMainRow[]`: outgoing rows on **main** accounts, newest first (`id` breaks ties), with the base — the settle / attach pickers and *Link payment* start from it and filter their own (settling rows, nothing left to allocate).
- `bookingDates(tx, ids)` → `Map<id, YYYY-MM-DD>`; unknown ids absent.
- `firstBookingDate(tx)` → `YYYY-MM-DD` of the first bank row, or null — the package's `firstMonth` reads it.
- `transactionStates(tx, ids)` → `Map<id, { state, allocated, inTransfer, partnerId, partnerName, partnerFrom, basCode, basFrom, mixed }>`: the derived state with the facts it comes from (Σ allocated FROM the row, the transfer leg, the effective partner and category — F129) — the package's bank sheet reads it instead of re-deriving them from the links; unknown ids absent.

## Linkable

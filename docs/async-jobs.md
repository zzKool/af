# Async jobs (pg-boss)

Decision D17 (2026-10-20): a Postgres-backed queue in the same container replaces Inngest. No external job service, no signing keys, works offline on the homelab, and survives the app being scaled to zero for weeks (constitution §1.9): jobs wait in `pgboss.job`, schedules catch up on the next start. Phase-0 item 4.1.

## Shape

```
src/kernel/jobs/
  types.ts      JobDefinition, ScheduleDefinition, EnqueueOptions, JobContext — the contract modules write against
  queue.ts      pg-boss behind that contract: startJobs(), enqueue(), stopJobs(), getBoss(); the ONLY importer of pg-boss (guard)
  context.ts    createSystemCaller(), withJobContext(tenantId, userId, cb) — RLS transaction + CallerIdentity + AuditLogger
  queue.test.ts real pg-boss against the test database (retry → dead letter, exclusive keys, schema version)
src/modules/<m>/jobs/<name>.ts   one JobDefinition per file; the module's index.ts exports `<m>Jobs` / `<m>Schedules`
src/instrumentation.ts           composition root: startJobs([...documentJobs, ...rateJobs], [...rateSchedules]) once per server process
prisma/migrations/20261020120000_add_pgboss/   the pgboss schema (generated by pg-boss, owned by the app role)
```

Queues today: `documents.process-document` (+ `.dead`), `rates.ecb-sync` (scheduled weekdays 16:30 Stockholm).

## Writing a job

```ts
// src/modules/<m>/jobs/<name>.ts
import { withJobContext } from "@/kernel/jobs/context";
import type { JobDefinition } from "@/kernel/jobs/types";

export interface MyJobData { tenantId: string; userId: string; entityId: string }

export const myJob: JobDefinition<MyJobData> = {
  name: "<module>.<verb>-<entity>",
  options: { policy: "exclusive", retryLimit: 3, retryDelay: 30, retryBackoff: true, expireInSeconds: 300 },
  handler: async ({ tenantId, userId, entityId }, { attempt }) => {
    // read the entity's status, do what is left, write the next status — in short transactions
    await withJobContext(tenantId, userId, async (tx, caller, audit) => { /* … */ });
  },
  onDeadLetter: async (data) => { /* leave the entity consistent after the last retry */ },
};
```

Rules:
- **A job carries ids only; the state machine lives on the entity.** Every attempt reads the status and does what is left, so a retry after a crash, a restart or weeks of downtime is always safe. (Inngest's memoised steps are gone — resumability comes from the entity, not from the queue.)
- **Throw to retry, return to complete.** A non-retryable outcome (auth failure, entity gone) is written to the entity and the handler returns. After `retryLimit` or when an attempt exceeds `expireInSeconds`, pg-boss moves the job to `<name>.dead` and `onDeadLetter` runs — the safety net that leaves no document in `processing` forever.
- **External calls outside transactions.** `withJobContext` opens a short RLS transaction (interactive-transaction timeout 5 s); OCR and ECB calls happen between two of them.
- `policy: "exclusive"` + `enqueue(job, data, { singletonKey })` = at most one job per entity queued, retrying or active; a duplicate enqueue returns `null`.
- `caller.source` is `"system"`; `userId` is the user who triggered the work (audit rows name them), never a service account.
- Register the job: export it from the module's `index.ts` (`<m>Jobs`) and list it in `src/instrumentation.ts`.

## Enqueueing from an action

```ts
ctx.onCommit(async () => {
  await enqueue(processDocumentJob, { tenantId, userId, documentId }, { singletonKey: documentId });
});
```
Always from `onCommit` (see [[architecture-decisions]] AD-1): a job that starts before the row is committed finds nothing.

## Schedules

```ts
export const ecbSyncSchedule: ScheduleDefinition<EcbSyncData> = {
  job: ecbSyncJob, cron: "30 16 * * 1-5", tz: "Europe/Stockholm", missed: "once",
};
```
`missed: "once"` (the default) is the catch-up: occurrences that came due while the app was down produce one job on the next start. A scheduled handler must therefore size its own work from the entity (the ECB job counts the weekdays since the last stored rate and fetches that many observations).

## Runtime

- One pg-boss instance per process, kept on `globalThis` (Next.js gives instrumentation and routes separate module graphs). `startJobs` is idempotent, logs and returns `false` instead of throwing — the app keeps serving pages when the queue is unavailable.
- `JOBS_DISABLED=1` skips the worker (builds, scripts, tests that never need it). `JOBS_POOL_MAX` (default 2) sizes pg-boss's own pool.
- pg-boss runs as the app role (`DATABASE_URL`) with `migrate: false`. The schema was installed by the `add_pgboss` migration, which `SET ROLE af_app` so the app role owns it (`createQueue` creates a partition per queue at runtime and needs ownership). **Upgrading pg-boss** = a new migration from `PgBoss.getMigrationPlans("pgboss", <stored version>)`; `queue.test.ts` fails when the package's schema version and the stored one differ.
- Inspect: `select name, state, retry_count, data, output from pgboss.job order by created_on desc;` — `output` holds the last error of a failed job. Dead-letter queues are plain queues: `select * from pgboss.job where name like '%.dead'`.

## Testing

- `queue.test.ts` (server project) drives real pg-boss: workers poll every 2 s, so job tests take seconds, not ms.
- Handler tests (`process-document.test.ts`) call `job.handler(data, ctx)` and `job.onDeadLetter(data, ctx)` directly with the DB, storage and OCR mocked — no queue involved.
- Pure logic (`observationsToFetch`) in `*.pure.test.ts`.

# Supplier invoices — payables keyed like expenses, paid by links, VAT for the declarations

Module `src/modules/supplier-invoices` · schema `prisma/schema/supplier-invoices.prisma` · migration `20261021160000_add_supplier_invoices` · spec `specs/supplier-invoices/` (spec, plan, tasks, screenshots) · decisions D8, D28, D-g (no paying-account constraint, cross-currency like D26).

> A supplier invoice is what a vendor sends AnalyticsFab: the accountant's monthly fee (`Factura 9160`), a SaaS invoice, the Swiss fiduciary. It is a reviewed document, the **partner** (type vendor), the supplier's **number** (unique per supplier), the dates and a **due date** defaulted from the partner's terms, an amount with **VAT** under a registration, in CHF / EUR / SEK, and the **bank rows that paid it** (`justifies` links). It lives in an expense **group** and keys like an expense in that group (`SI213-Acc-01`, the per-group × alias counter is shared, D28). *Unpaid / partially paid / paid / overdue* are **derived** from the links and the due date; `cancelled` is the only typed flag. The SEK base is written once (ECB of the invoice date), or replaced by the bank's when a cross-currency payment is attached.

## Model

```
supplier_invoices        group_id (FK → expense_groups) · key (`SI213-Acc-01`, unique) · seq · alias (snapshot)
                         partner_id (validated UUID, type vendor) · invoice_number (unique per tenant + partner; case- and space-insensitive in the service)
                         invoice_date · due_date (≥ invoice_date) · due_date_defaulted · currency
                         amount_net · vat_amount (≥ 0) · amount_total (= net + VAT ± 0.01, > 0)
                         amount_base · rate · rate_source ∈ same_currency | ecb_daily | ecb_nearest | bank | manual (the shared Postgres enum, F67) · rate_date?
                         paid_amount? / paid_currency? (the bank row's, once a cross-currency payment is attached)
                         bas_code · vat_registration_id? (validated) · document_missing · note?
                         cancelled · cancelled_reason? · cancelled_at?
supplier_invoice_lines   invoice_id (FK CASCADE) · line_no (unique per invoice) · description · amount_net · vat_rate (%) · vat_amount · bas_code
partners                 + payment_terms_days? (0–365; the due-date default, 30 when blank)
```

Triggers: `supplier_invoices_lock_key` (key, seq, alias, group never change), `block_delete_when_linked('supplier_invoice')`. RLS everywhere. Lines are intra-module (a VAT / category split, none by default); money immutability once paid is a **service rule** (`isOpen`: no `paid_amount`, no `justifies` link), the cancel flag and the links are the audit trail.

## Keys, bases, rules — `supplier-invoices.ts`

`supplier-invoices.ts` is a 19-line barrel of **named** re-exports (F50-i, 2026-10-23; the same 20 names as before the split): `create` · `update` · `lifecycle` (delete, cancel, uncancel) · `reads` (one invoice, copy last) over `validation` (amounts, lines, alias, supplier, registration, `checkDuplicateNumber`, `isOpen`) · `rate-base` (`baseAmount`, `baseFor`, `rebase`) · `schemas` · `dto` (+ `iso`) · `errors`. The helpers the parts share stay out of the barrel.

- `createSupplierInvoice(input)`: the partner must carry the type `vendor`; the alias comes from `settings.basAlias` (short code, else the curated suggestion; none → refused with a pointer to Settings → BAS); net + VAT = total within 0.01; lines, when given, must sum to net and VAT (± 0.01) and each line's category must exist; the VAT registration must be the tenant's; the number must be new for that supplier (case- and space-insensitive — *Invoice 9160 of this supplier is already recorded as SI213-Acc-01*); the currency defaults to the partner's, then SEK; the due date defaults to `invoice_date + payment_terms_days` (30 when unset) and is flagged `due_date_defaulted`; the base is `rates.rateToBase` of the invoice date (`ecb_daily` / `ecb_nearest` with the actual day, SEK → 1, a typed rate → `manual`, no rate → refused). The key: `nextInSeries(expenseSeries(group, alias))` → `supplierInvoiceRef` ([[numbering]]), taken after validation inside the transaction — an `Ex213-Acc-01` already in the group makes the first `SI213-Acc-02`. From a document (D27, D28): `documents.assignBusinessKey` renames it `SI213-Acc-01_2026-07-24_Skattepunkten_Office_Services_AB` (the file keeps its extension) and `created_from` supplier_invoice → document is written; one origin per document; a later failure throws `RollbackError`. Audited.
- `updateSupplierInvoice`: category (the alias stays), VAT registration, `document_missing`, note always; partner, number, dates, currency, amounts, rate, lines only while **open** (D37: a draft until its first payment) — the lines replaced. The base on an edit (`rebase`, F59): a typed rate → `manual`; another currency, or another invoice date on an ECB rate → the ECB of that date; anything else keeps the stored rate, source and rate date, and only the base follows a new total — a manual rate is never replaced by an edit that did not touch it. The due date on an edit: a typed one wins and clears `due_date_defaulted`; a **defaulted** one follows a new invoice date or supplier (`invoice_date + payment_terms_days`, 30 when unset); a typed one is never re-defaulted. `deleteSupplierInvoice`: refused once a paid amount or any link but its `created_from` exists (*cancel it instead*); otherwise the `created_from` link goes through `linking.removeLink` (D36, T020: the document is back in the inbox as *ready*, its `SI…` key kept), then the row — deleted and audited, the key never reused. `cancelSupplierInvoice(id, reason)`: open invoices only; `uncancelSupplierInvoice` reverses it. `copyLastPrefill(partnerId)`: the supplier's latest non-cancelled invoice as a prefill (currency, amounts, category, registration, note, group) — a new number and dates.

## Payments — `payments.ts`

- **Same currency** — `recordPayment({invoiceId, bankTransactionId, amount?})`: an outgoing row of the invoice currency; one `justifies` link bank_transaction → supplier_invoice allocating `amount` (default `min(|row|, open)`) in the invoice currency, never beyond what is open; instalments and batch payments are several allocations (a −100.00 row can pay 50.00 of one invoice and 50.00 of another — the picker shows what is left on the row). When the allocation leaves `0 < open ≤ settlement tolerance` the link carries the rounding note (*Rounding adjustment: CHF 0.05 (settlement tolerance)*) and the invoice derives `paid`. `removePayment({invoiceId, linkId})` reopens it by that amount.
- **Another currency** (D-g = D26) — `attachPayment({invoiceId, bankTransactionId})`: the row's amount becomes `paid_amount / paid_currency`, its journal base the invoice's `amount_base` (`rate_source = bank`), one link allocating the paid amount in the paid currency — paid. Refused when a same-currency payment exists (remove it first); a second attach is refused. `detachPayment(invoiceId)` removes the links and restores the ECB base of the invoice date.
- **Only these four write a payment** (D37, F58): linking refuses a generic `justifies` onto a supplier invoice both ways (the inbox's apply, *Link to…*, *Unlink* — an unlink of an attached row would have left `paid_amount` and the bank base behind). The linking inbox opens `/supplier-invoices?open=<invoice>&attach=<row>` instead — the row preselected in *Link payment*. A journal-entry payer (counted by `allocated.ts`) has no write path of its own now.
- Both refuse incoming rows and cancelled invoices. The linkable's amount is `paid_amount ?? amount_total` in the matching currency, so the linking module's allocation checks line up with the derived status.

## Status and reads — `status.ts`, `queries.ts`

`deriveSupplierInvoiceStatus({cancelled, total, allocated, dueDate, today})` → `{status, daysOverdue}`: `cancelled` first; `paid` when Σ allocations reach `total − settlementTolerance(total)`; `overdue` (with the days) once `due_date < today` and not paid — a partial payment is still overdue; else `partially_paid` / `unpaid`. Open (never negative), the settled test and the day arithmetic are the kernel's: `openAmount` / `isSettled` (`kernel/money/settlement`), `addDays` / `daysBetween` (`kernel/clock/calendar`).

## The duplicate check — `duplicates.ts` (specs/documents US3, D32 — 2026-10-21)

`findSupplierInvoiceDuplicates(tx, { documentId?, partnerId?, invoiceNumber?, amount?, currency?, date? })`, pure core `evaluateSupplierInvoiceDuplicates` (tested on `specs/documents/fixtures/duplicate-check-cases.json`): **exact** — same partner and `normaliseInvoiceNumber` (trim, collapse spaces, case-fold) → *high*; **hash** — the same bytes already became a supplier invoice → *high*; **fuzzy** — same partner, same currency, amount within ±1 %, date within ±7 days → *medium*; a cancelled invoice counts for **exact** only (it keeps its number — the unique index), never for hash or fuzzy; exact before hash before fuzzy, one entry per entity, max five. `checkSupplierInvoiceDuplicatesAction`; `createSupplierInvoice` takes `duplicateAck` like expenses — for **hash / fuzzy** only: an **exact** match is refused with or without it (D35; `checkDuplicateNumber` — the same `normaliseInvoiceNumber` (`invoice-number.ts`) as the finder since audit 32, so `91 60` and `91  60` are one number for both — + the unique index on the raw number) (the schema is declared locally — the two modules meet through the linking registry at module load, so nothing from expenses is used at the top level). `NewSupplierInvoiceDialog` takes `initial` and shows the `SupplierMatchCard` ([[partners]]). An exact match shows `ExactNumberStop` (`components/exact-number-stop.tsx`, T019 / D35, 2026-10-23): *the number is already recorded*, a link to the invoice that holds it, no note, *Create* disabled; hash / fuzzy go to expenses' `DuplicatePanel` (*Create anyway* with a note on *high*, a warning on *medium*).

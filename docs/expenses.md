# Expenses — groups, payers, the owner's liability, settlements, the reimbursement statement

Module `src/modules/expenses` · schema `prisma/schema/expenses.prisma` · migrations `20261021120000_add_expenses_and_traktamente`, `20261027200100_link_payment_record` (F114) · spec `specs/expenses/` (harvest, spec, plan, tasks), `specs/linking/payment-record.md` (F114, D60: the link as the only payment record) · decisions D26, D27, D28, D60. Part 1: model, keys, bases, derived status, ledger, settlements, statement job, linkables, queries. Part 2: the pages (`/expenses`, the groups, the group page with the trip panel — [[traktamente]] — the settle page, the settlements, the statement print route).

> An expense is one cost the company bears outside supplier invoices: a receipt, the per-diem of a trip, a Swiss VAT payment. It lives in a **group** (`213 — Travel to CH in March 2026`), carries a **key** that is the receipt's file name (`Ex213-Tr-01`), a **base at its date** (written once, never the bank's — F114) and a **payer**: a bank account, the company's main ones (`Plusgirokonto SEK`, `Plusgirokonto CHF`) or a private instrument of the owner (`Private SE`, `Private CH` — `bank_accounts.role = owner_private`, [[banking]]). **The payment is a link and only a link** (D60): a `justifies` link from the paying bank row (company-paid), a `settles` link from the refund row (private) — each with the amount it pays in the expense's currency and the base the row gave. What the owner paid privately is a liability of the company in base; a refund transaction **settles** a chosen set of those expenses; the residual stays open. *Paid / awaiting link / to refund / partially refunded / refunded*, what is open and the **FX difference** are **derived** from the links, never typed.

## Model

```
expense_groups     number (series `expense_group`, never reused) · description · kind ∈ trip | batch
expenses           group_id (FK) · key (`Ex213-Tr-01`, unique) · seq · alias (snapshot) · kind ∈ receipt | per_diem | vat_payment
                   date · description · bas_code · amount (> 0) · currency · vat_amount? · vat_registration_id?
                   amount_base · rate · rate_source ∈ same_currency | ecb_daily | ecb_nearest | manual (CHECK `<> 'bank'`, F114) · rate_date?
                   paid_from_account_id (composite FK → bank_accounts, RESTRICT, D63: a main account or an owner_private one)
                   document_missing · partner_id? (F87: a vendor, validated UUID through partners, no FK; CHECK: never on a per_diem) · note?
settlements        number (`ST26-001`, series `ST{yy}`) · bank_transaction_id (composite FK → bank_transactions, RESTRICT; one active per row)
                   note? · status ∈ active | cancelled · cancelled_at? · statement_document_id? (set once by the job)
                   — *superseded* is derived, `cancelled && statement_document_id`; Σ base, the rounding and the FX difference are derived from the links
links              the payments (owned by [[linking]]): `justifies` / `settles` bank_transaction → expense with allocated_amount (the expense's currency), allocated_base (what the row gave)
```

Gone with F114 (D60): `payment_sources` (the payers are bank accounts), `settlement_lines` (the lines are the `settles` links), `paid_amount` / `paid_currency` / `base_provisional` (the link carries the payment, the base is final at creation), the settlement's `refund_*` / `allocated_base` / `exchange_difference_*` / `rounding_base` (derived).

Triggers: `expenses_lock_money_when_linked` — the one `lock_money_when_linked()` shared with supplier invoices (amount, currency, VAT, date, base, rate, payer, group never change once an allocating link points at the row: the same fact as the service's `isOpen`, F62 / D37 / F114), `expenses_lock_key` (key, seq, alias never change at all), `settlements_lock` (number and row written once; `statement_document_id` NULL → value; a cancelled settlement stays cancelled), `block_delete_when_linked` on both; no DELETE grant on `settlements`; `links_check_allocation` on every link (Σ amount onto the expense ≤ its amount, Σ base from the row ≤ its base). RLS everywhere.

## Keys and bases — `expenses.ts`

- The key: `nextInSeries(expenseSeries(group, alias))` → `exg-213-Tr` → `Ex213-Tr-01` ([[numbering]]). The alias is the category's short code (`settings.basAlias`: the tenant's short code, else the curated suggestion; a category without one is refused with a pointer to Settings → BAS). It is a **snapshot**: changing the category later never changes the key. The counter is taken after validation, inside the transaction — a rollback hands it back, a delete never does.
- The base: `rates.rateToBase` of the expense date, whoever pays (`ecb_daily`, or `ecb_nearest` with the actual date; SEK → 1 `same_currency`; a typed rate → `manual`) — written once, never replaced by the bank's (F114, D60; the CHECK says so). What the bank paid lives on the link: `payExpense({expenseId, bankTransactionId, amount?, amountBase?})` writes one `justifies` link bank_transaction → expense — `allocated_amount` in the expense's currency (default: what is open, no more than the row has left when the currencies match), `allocated_base` what the row gave (default: the row's base pro rata, the exact remainder for the link that exhausts the row; the row's whole remaining base across currencies). D26's card receipt: 45.00 CHF at an ECB base of 523.17, the SEK card row −531.40 → the link says 45.00 CHF · base 531.40, the receipt keeps 523.17, the difference +8.23 is derived (the card's margin). Several rows may pay one expense (a deposit and a balance), one row several expenses (two receipts on one card row). `unpayExpense({expenseId, linkId})` removes one link — nothing on the expense moved, nothing to restore. The row must be outgoing and on the payer's account. **Only these two write that link** (D37, F58): linking refuses a generic `justifies` onto an expense both ways (the inbox's apply, *Unlink*), and the inbox opens `/expenses?open=<expense>&attach=<row>` instead — the row preselected in *Pay with this row*.
- From a document (D27): `createExpense({documentId})` renames the uploaded receipt to `Ex213-Tr-01_2026-03-10_` (`documents.assignBusinessKey`, the file keeps its extension) and links `created_from` expense → document; one origin per document. A later failure in that chain throws `RollbackError`.
- **The receipt after the expense** (F94 FR-012, `specs/subscriptions`): `attachDocument({expenseId, documentId})` makes an inbox receipt what `createExpense({documentId})` would have — renamed `{key}_{date}_`, `created_from` — and clears `document_missing`; in every state (proof, not a money fact — the lock trigger's columns untouched); refused when the expense has its document or the receipt became something. `detachDocument({expenseId})` removes the link: back in the inbox as *ready*, its key kept. The panel's Proof: *Attach receipt* (the inbox's expense documents, `candidateExpenseDocumentsAction`) / *Remove receipt* (owner).
- `updateExpense`: description, category, note, `document_missing` always; amount / currency / date / payer / rate / VAT only while the expense is **open** — the base is recomputed. **Open** is one rule (`isOpen` / `isExpenseOpen`, D37, F62, F114): no allocating link onto it (`justifies` from its paying row, `settles` from a refund row); the lock trigger tests the same fact, the panel reads `ExpenseDetail.isOpen` instead of guessing. `deleteExpense`: open expenses only (*paid or refunded*); a `created_from` link alone does not block (D36, T020), nor an `occurrence_of` (F94 — an attribution to a subscription, the period is due again) — they go through `linking.removeLink` before the delete, and the receipt is back in the inbox as *ready*, corrections and its `Ex…` key kept; any other link refuses (*linked*). `createPerDiemExpense` / `replacePerDiemExpense`: what [[traktamente]] writes (kind `per_diem`, SEK, the owner's private instrument in the base currency; replaced only while open).
- Groups (`groups.ts`): number from `expense_group` (`numbering.EXPENSE_GROUP_SERIES`), deletion refused while expenses exist, a group with a trip stays a trip group. The payers come from banking (`banking.payerAccounts` / `payerAccount`: the main accounts and the owner's private instruments, never savings; `createPrivateAccount` under Settings → Bank accounts → *Private instruments* — F114 US4); `resolvePayer` validates `paid_from_account_id`.

## Status and the ledger — `status.ts`, `queries.ts`

`deriveExpenseStatus({paidByPrivate, amount, allocated})` — amounts in the expense's currency, Σ of its allocating links (F114): company-paid → `paid` when the links cover the amount within the one tolerance (`isSettled`, `kernel/money`: max(0.05, 0.5 %)), else `awaiting_link`; private → `refunded` when they do, `partially_refunded` when some of it is allocated, else `to_refund`. **Open** is one rule (`openOn` in `status.ts`: the remainder in the expense's currency, 0 within the tolerance) and the owner's claim in base follows it (`openBase`: the expense's base for the share not yet refunded — `kernel/money` `fxDifference` / `expectedBases`: pro rata of the amount, the exact whole once covered, a same-currency slice's base taken as it is when within the tolerance of pro rata). The list's *Owed (SEK)* and its sum, the groups, the ledger, the expenses a settlement proposes and the status all read these; the allocating links are one query, `linking.allocationsOnto`, for all of them and the statement. A 0.30 residual is *refunded* and 0.00 everywhere. The **FX difference** of an expense (`fxDifference`: Σ base the rows gave − the base the books carry for the paid share, signed — > 0 a loss 7960, < 0 a gain 3960; within the tolerance rounding) is a list column and a line under the panel's payments.

`ledgerSnapshot(tx)`: per private instrument and in total — `openBase`, `allocatedBase`, `openCount` — plus the count of company-paid expenses still awaiting their bank row (the package's `notes.md`, the dashboard's action item). `openPrivateExpenses(sourceId?)` is the settle page's left column. `inputVatSources({registrationId, from, to})` — the expenses carrying VAT under a registration, by date (key, description, date, amount, VAT) — the Swiss return's ref. 400 drill-down ([[exports]]).

`EXPENSE_COLUMNS` + `listExpenses` / `distinctExpenseValues` / `expenseDateHierarchy` (two-step list: stored columns in SQL, then group, payer, BAS label, Σ lines, Σ justifies, document joined over the set; derived filters / search / sort / page / sums in memory, cap 20 000). `getExpenseDetail` (status, allocated / open / base / FX difference, document, links with the other side's label, the `payments` — one per allocating link: the row, its date, what it pays, the base it gave — and the settlements it took part in), `listGroups` / `getGroupDetail` (totals per currency and in SEK, open base, `hasTrip`), `listSettlements`, `settleableTransactions` (`banking.outgoingMainRows` minus the rows of an active settlement), `resolveStatement`. Other modules' tables are read through their read API only (lessons audit 22–25): links through `linking.linksTouching` / `createdFromTargets` / `linksWithLabels`, bank rows through `banking.outgoingMainRows` / `bookingDates` / `getBankTransaction`, the receipt through `documents.getDocument`.

**Reverse charge (D54, F91).** An expense made from a document that says the buyer pays the VAT carries the flag: the derived `reverseCharge` column (a *Yes* tag, filterable) and a *Reverse charge* tag in the panel's title. The rule is the document's — `documents.reverseChargeDocumentIds` over the `created_from` targets, the OCR's reading as corrected on review — so clearing it on the document clears it here. Nothing is computed from it: the treatment stays the accountant's (D23).

## Settlements — `fifo.ts`, `settlement-math.ts`, `settlements.ts`

Pure (`fifo.ts`, property-tested): `fifoAllocate(open, refundBase)` — expense date then key, `min(open, remaining)` each, stops when the refund is used up. `settlement-math.ts` (client-safe, the settle page runs the same figures): `amountForBase(e, base)` — what a base slice refunds of the open claim (the share; the whole open amount when the base covers it within the tolerance), `expectedBaseFor(e, amount, base?)` — the base the books carried for it (the whole open claim when covered; pro rata, or the base given when within the tolerance of it), `settlementTotals(lines, refundBase)` — Σ base, Σ expected, the signed **difference**, `rounding` within the tolerance, what the row keeps unallocated — and `differenceBasCode` (3960 when the company paid less base than the claim, 7960 when more).

**A settlement is the numbered statement over the `settles` links of one refund row** (F114, D60). `proposeSettlement({bankTransactionId, paidFromAccountId?, expenseIds?})` (nothing written) → the refund row (outgoing, main account, not already settling; its base) and the FIFO lines over the open private expenses (of the instrument / the ticked ids), each with the amount its base covers. `confirmSettlement({bankTransactionId, lines: [{expenseId, allocatedBase, allocatedAmount?}], note?})` validates every line (a company-paid expense, a duplicate line, an amount beyond what is open, Σ base beyond the row's → refused with the matching message), takes `ST{yy}-nnn` (`settlementSeries` of the booking date), writes the row, then one `settles` link per line in FIFO order — `allocated_amount` what it refunds (the share the base covers, or the whole open amount when the owner says *in full*: a cross-currency refund of less base than the claim), `allocated_base` the base given, the note `Settlement ST26-001` — audits; the action enqueues `expenses.render-statement` on commit. **No confirmation step**: the difference is derived and signed, the sign says the account, the statement prints it. `cancelSettlement`: the links removed, status `cancelled`, the balances reopen, the number stays, the statement is kept (retention, D26) and reads **superseded** — derived, `cancelled && statement_document_id` (`isStatementSuperseded`, F62), so a statement the job stores after the cancel is superseded too. `settlementDtos` reads a set of settlements with their rows' facts and their lines (the links, with the base the books carried per link — the kernel's `expectedBases` over every allocation onto the expense).

The owner's fixture (`specs/expenses/fixtures/owner-flow-settlement.json`): 6 450 + 1 620 + 2 695 SEK of private CHF receipts; variant A −9 700 SEK → 6 450 / 1 620 / 1 630 (151.21 CHF of the meals), residual 1 065; variant B −1 000 CHF at 10.70 (base 10 700) → FIFO 6 450 / 1 620 / 2 630, the meals *in full* → all refunded, difference −65.00 (3960); variant C at 10.7647 (10 764.70) → the meals' 2 694.70 covers the claim within the tolerance → all refunded, −0.30 rounding.

## The statement — `statement.ts`, `jobs/render-statement.ts`

`resolveStatement(tx, caller, id)` → number, company, payee (the instrument(s) of the refunded expenses), the refund row, the lines in `fifoOrder` (key, date, description, group, category, amount, base, what this settlement refunds, the base given, the base the books carried, what is still **owed** after every allocation — `openBase`, so a remainder within the tolerance prints 0.00 like the list and the ledger, F88 / D47), the totals (Σ base, Σ expected, the signed difference with its BAS, or the rounding), the residual (their sum). The job `expenses.render-statement` (registered in `instrumentation.ts`): only active settlements without a statement; renders `/print/settlement/[id]` through `kernel/pdf` (the renderer is injectable for tests), stores `Reimb_ST26-001_2026-03-31.pdf` through `documents.storeGeneratedDocument` (`generated`, financial, prefix `expense`), sets `statement_document_id` once (the lock refuses a second), links `justifies` bank_transaction → document — the justification the refund never had. Idempotent across retries. The print route and `StatementSheet` come with part 2.

## The duplicate check — `duplicates.ts` (specs/documents US3, D32 — 2026-10-21)

`findExpenseDuplicates(tx, { documentId?, merchant?, amount?, currency?, date? })` → `DuplicateMatch[]`: **hash** — the documents holding the same bytes as the source (`documents.sameContentDocumentIds`) that already became an expense (`created_from` links read through `linking.linksTouching`) → *high*; **fuzzy** — same currency, amount within ±1 %, date within ±7 days (inclusive) and the same merchant name (`foldName`: trim, collapse, case-fold) → *medium*. `dedupeMatches`: one entry per entity (the first strategy wins), high first, at most five. The pure rules (`isNear` — days by the kernel's `daysBetween`, `foldName`, `dedupeMatches`, `createdFromTwins`) are exported for supplier invoices. `checkExpenseDuplicatesAction` serves the dialog; `createExpense` takes `duplicateAck { entityIds, note }` — the note is stored first in `note` (*Not a duplicate: …*, `noteWithAck`) and in the audit row's `duplicateAck`. The shared `DuplicatePanel` + `useDuplicateCheck` (`components/duplicate-panel.tsx`) render the matches with their reasons (dictionary keys with parameters) and the required note. `NewExpenseDialog` takes `initial` (the review page's *Make it…*, [[document-review]]).

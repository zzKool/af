# Linking — the single link table

Module `src/modules/linking` · schema `prisma/schema/linking.prisma` · migrations `20261020060000_add_links`, `20261020190000_add_created_from_link_kind`, `20261026200000_add_subscriptions` (the `occurrence_of` kind) · phase-0 item 3c · spec `specs/linking/` (suggestions, part 1) · decisions D18, D25, D27.

> Linking is the product (constitution §1.2). The `links` table is the one source of truth for relationships between documents, bank transactions, journal entries, invoices, supplier invoices, expenses, settlements, partners and contracts. Everything above it — suggestions, the graph, the accountant package — is a read model.

## Model

```
links (tenant_id, from_type, from_id, to_type, to_id, kind, allocated_amount, currency, note, created_at, created_by, source)
  kind ∈ justifies | transfer | settles | belongs_to | created_from | occurrence_of   (CHECK constraint)
  unique (tenant, from, to, kind) · RLS tenant_isolation · immutable rows (change = remove + create, both audited)
```

Endpoints are polymorphic (`type` + `id`) — no cross-table foreign keys (RLS blocks them). Existence is checked through the owning module's registered `Linkable`.

| kind | from → to | allocation |
|---|---|---|
| `justifies` | bank_transaction / journal_entry → document / invoice / supplier_invoice / expense | yes — against the target's amount |
| `transfer` | bank_transaction → bank_transaction (`CHANGE CHFSEK` pairs, debit → credit; [[banking]] `acceptTransfer`) | no |
| `settles` | bank_transaction → settlement (owner reimbursement) | yes |
| `belongs_to` | document / invoice / supplier_invoice / expense → partner / contract | no |
| `created_from` | expense / supplier_invoice → document ("what this document became", D27) | no — and exclusive: one origin per document, one document per entity |
| `occurrence_of` | expense / supplier_invoice → subscription ("which subscription this is a period of", F94, D57) | no — exclusive on the entity: one subscription per entity; an attribution, never proof — it goes with a deleted expense / supplier invoice like `created_from` |

The matrix lives in `kinds.ts`; a new linkable type is one line there plus a `Linkable` in its module.

**Why "what a document became" is a link and not a column (D27).** A `became_type/became_id` pair on `documents` plus a `document_id` on every entity would be the same fact stored twice, with its own delete guard, its own audit and its own "show me everything connected to this" query. As a `created_from` link it gets all three from the one table, the document review screen reads *became expense Ex213-Tr-01* from `getLinksFor`, and the graph / package read models see it like any other edge. The exclusivity (a document becomes one thing) is a partial unique index, so it holds even for a direct SQL insert.

## Invariants — where each one lives

| Invariant | Service (`linking.ts`) | Database |
|---|---|---|
| only `modules/linking` writes `links` | guard test `linking owns the link table` | grants: app role has SELECT/INSERT/DELETE, no UPDATE |
| both endpoints exist in the caller's tenant | `Linkable.exists` / `summary` through the registry | RLS on every table |
| kind accepts the pair | `isKindAllowed` | `links_kind_check` |
| allocation > 0, currency matches the target, Σ allocations ≤ target amount | `canAllocate` (property-tested in `allocation.pure.test.ts`) | `links_allocation_positive_check`, `links_allocation_currency_check` |
| Σ allocations **from** one source ≤ its amount, same currency (a bank transaction, a manual journal entry) | `createLink` checks the source's summary too (R19) | service-level — polymorphic sources have no single table to read in a trigger; the target side stays DB-checked |
| no self-link, no duplicate | explicit check / `DUPLICATE_ENTRY` | `links_not_self_check`, unique index |
| `created_from` is exclusive on both ends | `EXCLUSIVE_KINDS` pre-check (`already became …` / `already created from …`) | partial unique indexes `links_created_from_origin_key`, `links_created_from_entity_key` |
| `occurrence_of` is exclusive on the entity | `EXCLUSIVE_KINDS` pre-check, on the side `EXCLUSIVE_SIDES` names (`from`) | partial unique index `links_occurrence_of_entity_key` |
| a linked document is never hard-deleted | `deleteDocument` translates the trigger into `BUSINESS_RULE_VIOLATION` | trigger `documents_block_delete_when_linked` (`block_delete_when_linked('document')`) — reuse it for every linkable table |
| every link / unlink is audited | `audit.log` create/delete with the endpoints | — |
| a `justifies` onto an **expense** or a **supplier invoice** is written and removed by its own module only (D37, F58) | `createLink` / `removeLink` refuse it unless `{ owner: <that type> }` is passed (`kinds.ts`: `OWN_PAYMENT_FLOW`, `needsOwnFlow`); the refusal carries `details.ownFlow` | — |

## Making a module linkable

```ts
// src/modules/<m>/linkable.ts
import type { Linkable } from "@/modules/linking";
export const invoiceLinkable: Linkable = {
  type: "invoice",
  exists: (tx, id) => tx.invoice.count({ where: { id } }).then((n) => n > 0),
  summary: async (tx, id) => { const i = await tx.invoice.findUnique({ where: { id } }); return i && { type: "invoice", id, label: i.number, amount: i.total.toString(), currency: i.currency }; },
};
```
Export it from the module's `index.ts`, add one line in `src/modules/linking/linkables.ts`, add the type to `LinkableType` and to the matrix in `kinds.ts`, and add the delete trigger to the table's migration. `amount`/`currency` non-null → the entity can receive allocations. Registration is **lazy** (`provideLinkables` with namespace imports, resolved on the first `getLinkable`): every module imports linking, so the import graph is cyclic and a direct read of `module.xLinkable` at import time could see `undefined` depending on which file a test loaded first.

Registered today: partner, contract, document, invoice, bank_transaction, journal_entry, expense, settlement ([[expenses]]), supplier_invoice ([[supplier-invoices]] — amount = `paid_amount ?? amount_total`, so a cross-currency payment attached the D-g way allocates in the paid currency).

## Suggestions — `scoring.ts`, `suggestions.ts` (specs/linking)

The generic finder over the registry: a `Linkable` may add `facts(id)` (what the scorer needs about one entity), `candidates(query)` (the entities a bank row of a direction could justify, dated inside a window) and `search(q)` (the *Link to…* picker). The linking module never reads another module's tables — it asks the linkables. Registered today: `bank_transaction` (the row: |amount|, the journal entry's SEK base, every text field Nordea gave, the entry's partner), `invoice` (issued / sent; invoices are paid by incoming rows, credit notes by outgoing ones), `supplier_invoice` (not cancelled), `expense` (company-paid, no bank row yet; window ± 10 days), `document` (financial uploads with an OCR total that became nothing and justify nothing).

**One scorer, both directions** (`scoreMatch(row, entity)`, pure, harvest §4.1 / §8.1): full reference in the row's text 40 (the invoice number, the supplier's number, the expense key), partial invoice number 20, partner name 25 (every text field — v1 skipped `sender` and never checked the client's name), a word of the entity's description 15 (`OPENAI *CHATGPT` ↔ *OpenAI subscription*; generic words excluded), amount 40 / 30 / 20 / 10 (< 0.1 % / 1 % / 5 % / else, relative to the entity, also against what is still open on a partly paid one), date 30 / 25 / 15 / 5 (0 / ≤ 2 / ≤ 5 / else days), currency −10 unless a reference matched. Cross-currency pairs are compared on their SEK bases (within 6 %, else only a full reference keeps them) and never allocated here — the entity's own *attach* does that (D-g, D26); a client invoice is paid in its own currency (B9). **An unknown currency** (`EntityFacts.currency: null` — a receipt OCR read no currency on, F61-b) is never compared on the amount, never penalised and never dropped: reference, name and date only; `proposedAllocation` is null, `applySuggestion` links it **without an allocation**, *Apply HIGH* skips it (`CURRENCY_MISMATCH`, *currency not read*). The renderers print an amount only through `components/money.ts` (`moneyText` — null for a currency `formatCurrency` cannot format, which used to throw). Confidence: HIGH = score ≥ 80, or a reference with ≥ 60 unless the amount is only approximate; MEDIUM ≥ 50; LOW otherwise. Ranking HIGH > MEDIUM > LOW, then score, then label (total). `specs/banking/fixtures/matching-cases.json` runs against it — the v3 deviations are written out in `scoring.pure.test.ts`.

`suggestionsForTransaction(id)` → the row (with what is left to allocate) and the top five candidates, each with `allocation = min(remaining on the row, remaining on the entity)`; `suggestionsForEntity(endpoint)` → the rows that could pay it; `searchLinkables(q, types?)`; `applySuggestion({bankTransactionId, to, allocatedAmount?})` → the `justifies` link (a document without an amount is linked without an allocation); `bulkApplyHigh(ids)` → applied / skipped (`NO_CANDIDATES`, `LOW_CONFIDENCE`, `AMBIGUOUS` when the top two HIGH scores are within 10, `CURRENCY_MISMATCH`, `OVER_ALLOCATION`, `ALREADY_LINKED`) / failed. Suggestions are computed on request — ≤ 50 candidates per type, no cache table. The windows and the date points count ISO days with the kernel's `addDays` / `daysBetween` (`kernel/clock/calendar`, audit 27, T014; `daysBetween` stays re-exported from `scoring.ts`).

**Expenses and supplier invoices pay through their own panel** (D37, F58 — audit 4). Their payment is more than a link: *attach* writes the bank row's paid amount, base and rate onto the entity with the link, *detach* takes both off; a same-currency supplier payment goes through `recordPayment` / `removePayment`. So linking's generic paths — `applySuggestion`, `bulkApplyHigh`, `createLinkAction`, `removeLinkAction` — refuse a `justifies` onto them (before: an inbox-applied link left a company-paid expense *awaiting link* for good, an *Unlink* left the paid amount behind). They are still suggested and found; the UI sends the owner to the entity: `attachHref(to, rowId)` = its panel with `&attach=<row>`, which preselects the row in *Attach bank row* / *Link payment*. *Apply HIGH* reports such a top candidate under *failed* with the service's message (no skip reason of its own — that needs a dictionary key). The deeper fix (paid derived from the link, the bank base a fact of its own) was not chosen.

**UI**: `SuggestionsSection` (for a row or for an entity — the chip, the reasons in the user's language, the allocation to edit, *Link*, *Link to…* with the search; an expense or supplier-invoice candidate shows *Open* — its panel, the row preselected — instead of *Link*) and `LinksList` (the links with the other side's label and *Unlink*; a payment of an expense or a supplier invoice shows *Open* instead). On the banking panel (what this row could justify) and on the invoice page (*Bank rows*: the rows that pay it). The accountant sees, the owner links.

**The D40 kit (F71, 2026-10-23, T012).** One map, `confidence-family.ts`: HIGH → *done*, MEDIUM → *progress*, LOW → *neutral* — how far the evidence goes; the row keeps banking's own state (*open* = attention). `ConfidenceLabel` renders it (`<StateLabel>`) on every suggestion, the inbox list and its detail. Keys: `label-key.ts` `splitLabelKey(type, label)` — the keyed types (invoice, supplier invoice, expense, settlement, document) lead their label with the key — and `EntityLabel` shows it as a `<CodeChip>` with the rest as text (the full label is the tooltip). Money: `components/money.ts` `moneyText` is `formatMoney` (`−2 312.43 SEK`; `signed` for bank rows; null without an amount or a currency, never a throw — an OCR `GBP` prints as read). Entity types are grey `<Tag>`s. The graph: nodes coloured by place in the monthly loop through the `--chart-*` tokens (money · sales · costs · proof · parties), never a palette colour; each ring row is *type tag · key chip (the row link → the entity, `graph-open`) · amount (`data-amount`) · ⋮* (`RowActionsMenu`: *Graph* re-roots, *Open*); the page's title row: *Links graph* + the root's key chip, its type tag, **one** primary *Open*. The inbox: underline tabs (the counts stay in the words, as the documents inbox), signed amounts without a colour, a partly linked row as banking's `TransactionStateLabel`, the selected document's *About* as a `DetailsSection`, the failed lines of *Apply HIGH* in `--destructive`.

## The inbox — `inbox.ts`, `/banking/inbox` (US3, harvest H7)

`inboxRows(tx)`: every main-account row that is *open* or *partially linked* (`banking.listTransactions` filtered to the main accounts **and** the derived state before it pages its 300 — transferred and *no document needed* rows stay out; until T016 the page came first and newer savings rows could crowd main ones out), scored in **one pass**: the bank facts in bulk (`factsMany`), one candidate pool per direction × type over the whole date span (`candidates` with the widened window), the pool filtered to each row's own window, ranked, the top five kept; sorted HIGH > MEDIUM > LOW > no candidate, then newest. `unlinkedDocuments(tx)`: financial uploads that became nothing and justify nothing (`documents.unlinkedFinancialDocuments`).

`InboxWorkbench` (work archetype): the rows on the left — date, signed amount, description · account, the top candidate's chip and label, `Enter` hinted on HIGH, a checkbox for the bulk bar — and the selected row in full on the right (`TransactionDetailView`, the same component as the banking panel: journal entry, suggestions, links, transfer proposal, rule). Keyboard, ignored while typing or inside a dialog: `j` / `k` (`↓` / `↑`) move, `Enter` applies the top candidate when it is HIGH (else a hint), `1`–`9` the n-th (an expense or supplier invoice opens its panel instead), `l` opens *Link to…*, `c` jumps to the category, `u` undoes the last link made on this page, `?` the help. *Apply HIGH matches* runs `bulkApplyHigh` on the ticked rows (all when none) and reports applied / skipped (with the reason and the service's detail) / failed. The *Unlinked documents* tab lists them with *Open document* and the rows that could pay the selected one. Reached from the banking toolbar (*Inbox*).

## The graph — `graph.ts`, `graph-layout.ts`, `/links/[type]/[id]` (constitution §1.2, D18)

The read model (nothing stored): `neighbourhood(tx, root, {depth = 2, maxNodes = 80})` walks the `links` table breadth-first from one entity — one `linksTouching` per type on the frontier per hop — and labels every node through its module's linkable (`summary`: label, amount, currency). Each node carries `depth` and `parent` (the first node it was reached from — the tree the picture is drawn along); edges carry the kind and the allocation; an edge whose far end the node cap cut is dropped, so the picture only shows what it names. `truncated` is true when the depth or the cap stopped the walk and more exists beyond the last ring. Depth is clamped to `GRAPH_MAX_DEPTH = 3` (`?depth=`), so a busy partner never returns the whole company. Null when the root does not exist in the caller's tenant (RLS).

`layoutGraph` (pure) places the root at the centre and each hop on its own ring; a node's angular sector is proportional to the leaves under it, children sit inside their parent's sector, the first branch starts at north. `LinkGraph` draws it as an SVG — tree edges solid, cross-edges dashed, the kind (and allocation) on the edge, one colour per type, the full label as the tooltip, a click re-roots — and, beside it, the same nodes as a list by ring with *Graph* (re-root) and *Open* (the entity's own page: `entityHref` — invoices, documents, partners and settlements have pages; expenses, supplier invoices and bank rows open their list with the panel on that row via `?open=<id>`). The list is the accessible form; the picture is `aria-hidden`. The page `/links/<type>/<id>` (`graphAction` for clients; `can(read, link)`) is reached from the *Graph* button next to every *Links* heading (banking panel, invoice page, expense and supplier-invoice panels).

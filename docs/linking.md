# Linking — the single link table

Module `src/modules/linking` · schema `prisma/schema/linking.prisma` · migrations `20261020060000_add_links`, `20261020190000_add_created_from_link_kind`, `20261026200000_add_subscriptions` (the `occurrence_of` kind), `20261027200100_link_payment_record` (F114: `allocated_base`, the two triggers) · phase-0 item 3c · spec `specs/linking/` (suggestions, part 1; `payment-record.md` — F114, D60: the link as the only payment record) · decisions D18, D25, D27, D60.

> Linking is the product (constitution §1.2). The `links` table is the one source of truth for relationships between documents, bank transactions, journal entries, invoices, supplier invoices, expenses, settlements, partners and contracts. Everything above it — suggestions, the graph, the accountant package — is a read model.

## Model

```
links (tenant_id, from_type, from_id, to_type, to_id, kind, allocated_amount, currency, allocated_base, note, created_at, created_by, source)
  kind ∈ justifies | transfer | settles | belongs_to | created_from | occurrence_of   (CHECK constraint)
  unique (tenant, from, to, kind) · RLS tenant_isolation · immutable rows (change = remove + create, both audited)
```

**The link is the only payment record** (F114, D60 — `specs/linking/payment-record.md`). An allocating link (`justifies`, `settles`) carries `allocated_amount` **in the target entity's currency** (what part of it this row pays), `currency` (the entity's) and `allocated_base` — what the bank row gave for it, in the tenant's base: the row's base pro rata for a same-currency slice (the link that exhausts the row takes the exact remainder, so Σ base of a fully used row equals its base to the cent), the row's whole remaining base for a cross-currency payment, or what the caller states. Nothing is written on the entity: its base is at its date (`rate_source` never `bank`); paid / open are Σ `allocated_amount` against the amount under the one tolerance (`kernel/money/settlement.ts`); the **FX difference** is Σ `allocated_base` − the base the entity carries for the paid share (`fxDifference` / `expectedBases`), signed, derived. A deposit and a balance, or two receipts on one card row, are two links.

Endpoints are polymorphic (`type` + `id`) — no cross-table foreign keys (RLS blocks them). Existence is checked through the owning module's registered `Linkable`.

| kind | from → to | allocation |
|---|---|---|
| `justifies` | bank_transaction → document / invoice / supplier_invoice / expense | yes — against the target's amount (its currency), the base against the row's |
| `transfer` | bank_transaction → bank_transaction (`CHANGE CHFSEK` pairs, debit → credit; [[banking]] `acceptTransfer`) | no |
| `settles` | bank_transaction → expense (a refund row reimburses a private expense of the owner; the settlement is the numbered statement over a row's `settles` links — [[expenses]]) | yes |
| `belongs_to` | document / invoice / supplier_invoice / expense → partner / contract | no |
| `created_from` | expense / supplier_invoice → document ("what this document became", D27) | no — and exclusive: one origin per document, one document per entity |
| `occurrence_of` | expense / supplier_invoice → subscription ("which subscription this is a period of", F94, D57) | no — exclusive on the entity: one subscription per entity; an attribution, never proof — it goes with a deleted expense / supplier invoice like `created_from` |

The matrix lives in `kinds.ts`; a new linkable type is one line there plus a `Linkable` in its module.

**Why "what a document became" is a link and not a column (D27).** A `became_type/became_id` pair on `documents` plus a `document_id` on every entity would be the same fact stored twice, with its own delete guard, its own audit and its own "show me everything connected to this" query. As a `created_from` link it gets all three from the one table, the document review screen reads *became expense Ex213-Tr-01* from `getLinksFor`, and the graph / package read models see it like any other edge. The exclusivity (a document becomes one thing) is a partial unique index, so it holds even for a direct SQL insert.

## Making a module linkable

```ts
// src/modules/<m>/linkable.ts
import type { Linkable } from "@/modules/linking";
export const invoiceLinkable: Linkable = {
  type: "invoice",
  exists: (tx, id) => tx.invoice.count({ where: { id } }).then((n) => n > 0),
  summary: async (tx, id) => { const i = await tx.invoice.findUnique({ where: { id } }); return i && { type: "invoice", id, label: i.number, amount: i.total.toString(), currency: i.currency }; },
};
```
Export it from the module's `index.ts`, add one line in `src/modules/linking/linkables.ts`, add the type to `LinkableType` and to the matrix in `kinds.ts`, and add the delete trigger to the table's migration. `amount`/`currency` non-null → the entity can receive allocations. Registration is **lazy** (`provideLinkables` with namespace imports, resolved on the first `getLinkable`): every module imports linking, so the import graph is cyclic and a direct read of `module.xLinkable` at import time could see `undefined` depending on which file a test loaded first.

Registered today: partner, contract, document, invoice, bank_transaction (its summary carries `amountBase` — the capacity its links' bases are checked against), expense ([[expenses]]), supplier_invoice ([[supplier-invoices]]) — an entity's summary exposes its own amount and currency, always (F114); subscription.

## Suggestions — `scoring.ts`, `suggestions.ts`, `window.ts`, `memory.ts` (specs/linking; F116 `one-engine.md`)

The generic finder over the registry: a `Linkable` may add `facts(id)` / `factsMany(ids)` (what the scorer needs about entities), `candidates(query)` (the entities a bank row of a direction could justify) and `search(q)` (the *Link to…* picker); the bank row's linkable adds `rowsByCounterparty(keys)` (the memory's rows). The linking module never reads another module's tables — it asks the linkables. Incoming rows look for `invoice` and `document` (credit notes), outgoing for `supplier_invoice`, `expense`, `invoice` (credit notes) and `document`. Registered today: `bank_transaction` (the row: |amount|, its SEK base, every text field Nordea gave, its partner, its counterparty key), `invoice` (issued / sent; invoices are paid by incoming rows, credit notes by outgoing ones), `supplier_invoice` (not cancelled), `expense` (company-paid), `document` (financial uploads with an OCR total that became nothing and justify nothing). Facts carry `partnerId` and, for an entity with terms, `dueDate` (F116).

**The payment window** (`window.ts`, F116 FR-001 — the answer to *an invoice on 30-day terms is never a candidate*, audit B1):

```
an invoice / a supplier invoice   [issue − 5, max(due + 10, issue + 60)]      paymentWindow(entity)
an expense / a document           [date − 10, date + 10]
a row booked in [from, to] reads  issued ≤ to + 5 ∧ (due ≥ from − 10 ∨ issued ≥ from − 60)   termsSpan(query)
                                  + any entity whose number is among the row's tokens   referenceTokens(texts)
                                  + the latest of the partners the memory remembers      rememberedPartners(memory)
```

`candidateQuery(direction, bookedFrom, bookedTo, references, partnerIds, limit)` builds one query per row (or per inbox span); `belongs(rowDate, tokens, memory, candidate)` keeps what lies in the window **or** carries a number from the text **or** belongs to a remembered partner; `dedupe` folds the three lookups.

**The counterparty memory** (`memory.ts`, F116 FR-004, D67): `memoryForKeys(tx, keys)` → per counterparty key, the partners its rows' allocating links reach, with how often — the rows by `rowsByCounterparty` (≤ 200 per key, newest first), the links of this module's table, the partners by each owner's `factsMany`. Nothing stored: a confirmation is a link, a removed link forgets. `memoryForRow(tx, rowId)` (+ `counterpartyMemoryAction`) is what the Justify panel proposes its partner from (*This counterparty was linked to OpenAI 39 time(s) before*).

**One scorer, both directions** (`scoreMatch(row, entity, memory?)`, pure, harvest §4.1 / §8.1, F116 FR-002): **every point is a claim and every claim is true.** Full reference in the row's text 40 (the invoice number, the supplier's number, the expense key), partial invoice number 20, partner name 25 — the whole name or one of its tokens (`nameTokens`: ≥ 4 characters, legal forms and trade words out; a row word equal to it, starting with it, or a ≥ 6-character truncation of it — `ANTHROPIC* CLAU` finds *Anthropic PBC*, `SKATTEPUNK` *Skattepunkten*), **linked to this partner before 25 — a reference** (D67), a word of the entity's description 15, amount 40 / 30 / 20 / 10 (< 0.1 % / 1 % / 5 % / **10 %**, relative to the entity, also against what is still open on a partly paid one; beyond 10 % nothing), the date inside the window only (`dateClaim`: same day 30 · within 2 days 25 · on the due date 30 · within the terms 15 · up to 5 days late 15 · up to 10 days late 5 · an entity dated once within 5 days 15, within 10 days 5; outside the window nothing), currency −10 unless a reference matched. **A pair whose only claim is its date is no suggestion** (before F116, any pair got 15 points with *Approximate amount match* and *N days apart* — audit B7). Cross-currency pairs are compared on their SEK bases (within 6 %, D67; else only a reference keeps them); a receipt read in another currency without a base gets one for the comparison (`withForeignBases`: its amount at the ECB of its date into the row's currency, then the row's own rate — audit B6). **They apply on a click** (F116 PR B, D60): `applySuggestion` → `crossAllocation` — the entity's open amount when the row's remaining base covers its open base within 6 % (the row's whole remaining base on the link, or only the entity's open base when the row is larger), else the share the row's base buys; the FX difference is derived (F114). *Apply HIGH* still skips a cross-currency top (`CURRENCY_MISMATCH`): a currency is decided by a click. **Incoming rows** have proofs beyond client invoices (FR-006): a document whose total is negative is a credit note — direction incoming, amount its absolute value — a vendor refund's proof (D67: the expense is not reduced; a rule categorises the row). **An unknown currency** (`EntityFacts.currency: null` — a receipt OCR read no currency on, F61-b) is never compared on the amount and never penalised: reference, name, memory and date only; `proposedAllocation` is null, `applySuggestion` links it **without an allocation**, *Apply HIGH* skips it (`CURRENCY_MISMATCH`, *currency not read*). The renderers print an amount only through `components/money.ts`. Confidence: HIGH = score ≥ 80, or a reference with ≥ 60 unless the amount is only approximate; MEDIUM ≥ 50; LOW otherwise. Ranking HIGH > MEDIUM > LOW, then score, then label (total). `specs/banking/fixtures/matching-cases.json` runs against it — the v3 deviations are written out in `scoring.pure.test.ts`; the F116 cases in `window.pure.test.ts`. The reasons are English data; `suggestions-section.tsx` maps them to keys (`linking.reason.*`, the parametrised ones by pattern).

`suggestionsForTransaction(id)` → the row (with what is left to allocate) and the top five candidates, each with `allocation = min(remaining on the row, remaining on the entity)`; `suggestionsForEntity(endpoint)` → the rows that could pay it; `searchLinkables(q, types?)`; `applySuggestion({bankTransactionId, to, allocatedAmount?})` → the `justifies` link (a document without an amount is linked without an allocation); `bulkApplyHigh(ids)` → applied / skipped (`NO_CANDIDATES`, `LOW_CONFIDENCE`, `AMBIGUOUS` when the top two HIGH scores are within 10, `CURRENCY_MISMATCH`, `OVER_ALLOCATION`, `ALREADY_LINKED`) / failed. Suggestions are computed on request — ≤ 50 candidates per type, no cache table. The windows and the date points count ISO days with the kernel's `addDays` / `daysBetween` (`kernel/clock/calendar`, audit 27, T014; `daysBetween` stays re-exported from `scoring.ts`).

**Expenses and supplier invoices pay through their own module** (D37, F58 — audit 4; F114; F124 (3), 2026-10-29). The link IS the payment, but the owning module validates the pair (the row on the payer's account, outgoing, what is open) and writes it with `{ owner }`: `expenses.payExpense` / `unpayExpense`, `supplierInvoices.recordPayment` / `removePayment`. The two linkables register those as `pay` / `unpay` on the `Linkable` contract, and linking's generic paths go through them: `applySuggestion` (so *Link* on a suggestion, *Apply HIGH*, *Link to…*, the inbox's `Enter` / `1`–`9`) calls `linkable.pay` when it exists and returns the link the module wrote; `removeLink` (so *Unlink* anywhere) calls `linkable.unpay` for a `justifies` onto them. The raw `createLink` without `{ owner }` stays refused — nothing writes such a link but the module. The *Open* detour of F58 (`attachHref`, `&attach=<row>`) is gone from the UI; `attachHref` stays for deep links.

**UI**: `SuggestionsSection` (for a row or for an entity — the chip, the reasons in the user's language, the allocation to edit, *Link* on every candidate, *Link to…* with the search) and `LinksList` (the links with the other side's label and *Unlink* on every link but `created_from`). On the banking panel (what this row could justify) and on the invoice page (*Bank rows*: the rows that pay it). The accountant sees, the owner links.

**The D40 kit (F71, 2026-10-23, T012).** One map, `confidence-family.ts`: HIGH → *done*, MEDIUM → *progress*, LOW → *neutral* — how far the evidence goes; the row keeps banking's own state (*open* = attention). `ConfidenceLabel` renders it (`<StateLabel>`) on every suggestion, the inbox list and its detail. Keys: `label-key.ts` `splitLabelKey(type, label)` — the keyed types (invoice, supplier invoice, expense, settlement, document) lead their label with the key — and `EntityLabel` shows it as a `<CodeChip>` with the rest as text (the full label is the tooltip). Money: `components/money.ts` `moneyText` is `formatMoney` (`−2 312.43 SEK`; `signed` for bank rows; null without an amount or a currency, never a throw — an OCR `GBP` prints as read). Entity types are grey `<Tag>`s. The graph: nodes coloured by place in the monthly loop through the `--chart-*` tokens (money · sales · costs · proof · parties), never a palette colour; each ring row is *type tag · key chip (the row link → the entity, `graph-open`) · amount (`data-amount`) · ⋮* (`RowActionsMenu`: *Graph* re-roots, *Open*); the page's title row: *Links graph* + the root's key chip, its type tag, **one** primary *Open*. The inbox: underline tabs (the counts stay in the words, as the documents inbox), signed amounts without a colour, a partly linked row as banking's `TransactionStateLabel`, the selected document's *About* as a `DetailsSection`, the failed lines of *Apply HIGH* in `--destructive`.

## The inbox — `inbox.ts`, `/banking/inbox` (US3, harvest H7)

`inboxRows(tx)`: every main-account row still to justify — *open*, *partially linked*, and since F129 *linked · no partner* and *no proof · no partner* (banking's `needsProof`; `banking.listTransactions` filtered to the main accounts **and** the derived state before it pages its 300 — transferred and *no document needed* rows stay out; until T016 the page came first and newer savings rows could crowd main ones out), scored in **one pass**: the bank facts in bulk (`factsMany`), the memory of every row's key in one read, one candidate pool per direction × type over the whole date span (`candidateQuery` over the span, with every row's tokens and remembered partners), the pool filtered to what `belongs` with each row, ranked, the top five kept; sorted HIGH > MEDIUM > LOW > no candidate, then newest. `unlinkedDocuments(tx)`: financial uploads that became nothing and justify nothing (`documents.unlinkedFinancialDocuments`).

## Justify from the bank row — `justify.ts`, `justify-rules.ts`, `JustifyPanel`, `ReadingDialog` (F97 → F131, specs/justify)

The row is the fact, the document its evidence (review 2026-10-26 §1.1): one panel on an open outgoing row — in the banking panel and the inbox's right pane, above *As the bank said* — five ways out. **Drop the proof** (`p`): the drop zone asks **what the paper is** first — *(•) Invoice ( ) Receipt*, *Invoice* selected by default (D75, O5; `PaperQuestion`, `PAPERS` / `DEFAULT_PAPER` / `prefixTypeOfPaper` in `justify-rules.ts`): the answer goes with the upload — `documents.uploadDocumentAction` with the type it implies (`invoice` or `expense`, what `/documents` shows) **and `paper` itself**, which `kernel/ocr`'s `ocrModelFor` honours over D69's file rule: *Receipt* → `prebuilt-receipt` even for a PDF, *Invoice* → `prebuilt-invoice` even for a photo (D75; the answer lives in the OCR job's payload only, the reading's `modelUsed` says what read it — [[ocr-processing]]; a duplicate upload reuses the existing document, read as it was); the panel polls `getDocumentForReviewAction` every 2 s until the OCR read it (60 s cap; `ocr_failed` falls through with empty readings), then the **reading dialog** opens (below). **A proof already in the inbox** (T008): before any upload the panel lists the inbox documents that score for the row (`suggestionsForTransaction`, the `document` candidates, three at most) with *Use it* — the dialog opens on that document, the upload step skipped, the paper radio set from the model that read it (T030, `paperOfReading` — an `expense` PDF read by the invoice model shows *Invoice*), else its stored type; a document dropped on the row but not turned into anything comes back here after a reload. When the dialog comes up the host refreshes the row (`onProofRead`), so *Suggestions* below sees the document too. **Pick what exists**: the *Suggestions* below (unchanged). **No proof needed** (`n`): the reasons — fee 657 · tax 251 · salary 721 · interest 831 · client paid · other — then **the partner line** (F129 US3, D73 (b): there is no proof to derive a partner from, so it is typed here, never without one): each reason proposes a partner **by type** from a fact, marked as a proposal — `proposedPartnerRole(reason, accountCurrency)` (`justify-rules.ts`, pure): fee / interest → the bank, tax → the Swiss FTA on a CHF account else Skatteverket, salary → the owner as employee (the four system partners [[partners]] seeds once per tenant, found by their role in `justifyOptions.partners`), client paid → the client (the counterparty memory's partner when it has one, *remembered (n)*), other → the memory's, else empty; a role whose partner was deactivated says so (`justifyOptions.inactiveRoles`) instead of proposing. *Done* waits for a partner. `noProofNeeded` (`noProofSchema.partnerId` required — *A partner is required — the statement is the proof, the partner says of what*) sets the flag, the reason's account and the partner on the row by hand (`banking.categorise`), refuses a **linked** row (*remove the link first*; a *no proof · no partner* row takes it again), and says whether no active rule hits the counterparty; the toast then offers *Create rule* (`createRuleFromTransactionAction` — the learned rule carries the partner). The reasons are offered on **incoming** rows too (a tax repayment, a client's refund, interest — `NO_PROOF_REASONS_INCOMING`, *client paid* first); `p` and `x` stay out there. **Receipt lost** (`x`): the dialog without a paper → the entity with `document_missing` — its partner picked in the dialog like any other (F129: every exit names one). **This row refunds me** (F131 §5.1, the fourth exit — T018): on an outgoing row while the ledger owes the owner something (`justifyOptions.openPrivateCount`, through `expenses.ledgerSnapshot`), the FIFO picker **in place** (T021, F172 — expenses' `RefundPicker`): the open private expenses oldest first, the FIFO proposed for this row's base (`proposeSettlementAction`), the ticks and each line's base editable, *Confirm* greyed while a line takes more than is open on it or the lines more than the row, then `confirmSettlementAction` — the settlement, its `settles` links and the statement exactly as the settle page writes them; the host reloads the row. What the compact picker leaves out (the instrument filter, the *in full* tick of a cross-currency refund, the note) stays on the settle page, one link away (`/expenses/settle?row=<id>`, preselected and locked — [[expenses]] *Pages*); the `settles` links make the owner as employee the row's partner (F129, derived on read).

## Consistency checks (F130) — `check-proof.ts` ([[review-2026-10-31]] §4)

`checkProof(input) → ProofWarning[]`, pure and client-safe: the bank row against the reading of the paper dropped on it, and against what the partner, the counterparty memory and the rules say. **Warn, never block** — *Confirm* stays available; every warning is one `{ code, facts }` whose sentence (`warningMessage(warning, t)`, keys `linking.checks.*`) says what was compared and the numbers, never "looks wrong" (the 10-26 rule: every claim is true). The caller gathers the facts (the reading dialog, through `proofFactsAction` — F131); the function only compares. At most one warning per check; an empty list is all green.

## Proposals — `proposals/`, the *Proposed* line (F98, `specs/ai`, [[local-ai]])

What the rules, the partner's default, the owner's own history and the local model propose for a bank row's **category** or **partner**. Linking owns the `proposals` table; it writes proposals and the owner's decisions, **never a row's facts** — accepting goes through banking's `categorise` (`by: manual`: the owner's key is the categorisation).

```
proposals  run_id · target (bank_transaction, composite FK RESTRICT — D63) · kind ∈ bas | partner
           payload (Zod per kind, parsed on read) · source ∈ rule | partner_default | memory | model
           confidence 0–1 · reason · model? · prompt_version? · facts_hash · decision? · decided_at? · decided_by?
           current = the newest per (row, kind) · open = current ∧ undecided ∧ the row still lacks that fact — derived
```

- **Stage 1** (`stage1.ts`, pure, inputs from banking's `proposalInputs`): the first active rule that would set the fact (1.00 — rules already run at import, so this is the rows imported before the rule), the partner's default category (0.95), the **history** — the same counterparty key's rows the owner set by hand, ≥ 2 rows agreeing ≥ 70 % → 0.6 + 0.1 · N (max 0.95). Two sources that disagree: the first wins, capped at 0.79 (never HIGH), the other an alternative.
- **Stage 2 — the model** (`stage2.ts`, `prompts/bas-proposal.ts`, F98 PR 2): the **category** of every open row stage 1 left without a current answer — a counterparty never seen before is proposed **from its first row**. The prompt's static part (the same for every row of a run — the server's cache): the instructions, the tenant's **active** accounts (`code English (Swedish)`, and the owner's *Use for* note once F126 adds it), up to eight of his hand-categorised rows (the newest per code); the row last (date, amount, bank text). The answer's code is an enum of the active set (the grammar cannot produce another; re-parsed with Zod); confidence capped at 0.95 (never above a partner's default). **No vendor, product or keyword is mapped to an account in code or prompt** — a test refuses any literal code in `prompts/`. Three steps: prepare (one short transaction, after stage 1), ask (no transaction, one row at a time, at most 60 per run — the nightly takes the rest; a timeout retried once; an unreachable model stops the run), write (a second short transaction, for the rows still open). A model proposal's facts hash is the row's facts + the prompt's (version, accounts, notes): not asked again while both are unchanged — current or rejected; a new active account or an edited note asks again. AI off → stage 1 alone, nothing waits.
- **On documents** (`documents.ts`, F126): an inbox document (a receipt, a supplier invoice — nothing made from it yet) gets the model's **category** too, so *New expense* / *New supplier invoice* opens with it. The question is the document's kind, vendor, line descriptions and total (`basProposalUserForDocument`), the static part the same as a bank row's. Not asked when the vendor matches a partner (`partners.matchPartners`, ≥ 60 %) with a default account — that default fills the dialog anyway — nor again on the same facts. Runs after OCR reads a document (documents' `setOnDocumentExtracted` hook, wired in `instrumentation.ts` → `linking.propose-for-documents`), with the nightly run and *Run now*. The table gained `document` as a target: one FK column per type (`bank_transaction_id`, `document_id`, composite, RESTRICT) kept equal to `target_id` by a CHECK; documents' delete drops them first (`dropProposalsForDocuments`). The dialogs read `documentBasHints` (code, reason, prefill = HIGH) through `MakeItOptions.basProposals`: the account heads the picker as *AI proposal* with its reason, HIGH fills the empty field (dashed, *Proposed by the AI*), a supplier's default replaces it, the owner's pick is his. **Saving decides it** (`decideDocumentProposal`, in the create's transaction): the proposed code kept → `accepted`, another → `rejected` — the eval and Settings → AI count both.
- **Eval** (`eval.ts`, `scripts/ai-eval.ts`): `npx tsx scripts/ai-eval.ts [--since 2026-01] [--limit N] [--model name]` where the app runs — the owner's hand-categorised rows replayed through stage 1 (his own row out of the history) and the model (his own row never an example); prints agreement per source, per confidence family and per BAS code, the model's p50 / p95 — **counts and codes only** (D51). Read only; exits 1 when the endpoint is unreachable.
- **Policy** (`policy.ts`): HIGH ≥ 0.80 (pre-filled while `PREFILL_HIGH` — the owner's answer of 2026-10-27, one constant), MEDIUM ≥ 0.55, LOW not shown. The source is shown as a word: *rule* · *partner default* · *remembered* · *proposed* (the model).
- **Runs** (`jobs/propose.ts`): `linking.propose-for-rows` after an import commits (banking's import action enqueues it), `linking.propose-nightly` at 03:30 Stockholm for every tenant's open rows (as its owner — `kernel/auth` `tenantOwners`), *Run now* on Settings → AI. A run writes nothing for a proposal still current and identical; a kind the owner **rejected** is skipped while the row's facts hash (category, partner, counterparty key, amount) is unchanged.
- **Accept** (`acceptProposals`, one transaction): the facts of the chosen proposals (or an alternative's code) through `banking.categorise`, the proposals `accepted` + one audit row each, and `proposeRule` when no active rule fits the row (the panel's toast offers *Create rule*). A proposal no longer current is refused. **Reject** records the decision + audit. The accountant reads, never decides.
- **Delete**: banking's `deleteImport` calls `dropProposalsFor` before deleting its rows (RESTRICT; D63 forbids the cascade).
- **UI**: `ProposalLine` above the category form in the panel and the inbox's right pane (Accept · Reject · the alternatives; the inbox's `a` / `r`), the form's pre-fill (dashed, *Proposed — not saved yet*), the transactions list's *Proposed* column (`ProposedCode`, filterable, sortable by confidence), Settings → AI (`AiSettings`: the endpoint's state, acceptance per source over 30 / 90 days, *Run now*).

## The graph — `graph.ts`, `graph-layout.ts`, `/links/[type]/[id]` (constitution §1.2, D18)

The read model (nothing stored): `neighbourhood(tx, root, {depth = 2, maxNodes = 80})` walks the `links` table breadth-first from one entity — one `linksTouching` per type on the frontier per hop — and labels every node through its module's linkable (`summary`: label, amount, currency). Each node carries `depth` and `parent` (the first node it was reached from — the tree the picture is drawn along); edges carry the kind and the allocation; an edge whose far end the node cap cut is dropped, so the picture only shows what it names. `truncated` is true when the depth or the cap stopped the walk and more exists beyond the last ring. Depth is clamped to `GRAPH_MAX_DEPTH = 3` (`?depth=`), so a busy partner never returns the whole company. Null when the root does not exist in the caller's tenant (RLS).

`layoutGraph` (pure) places the root at the centre and each hop on its own ring; a node's angular sector is proportional to the leaves under it, children sit inside their parent's sector, the first branch starts at north. `LinkGraph` draws it as an SVG — tree edges solid, cross-edges dashed, the kind (and allocation) on the edge, one colour per type, the full label as the tooltip, a click re-roots — and, beside it, the same nodes as a list by ring with *Graph* (re-root) and *Open* (the entity's own page: `entityHref` — invoices, documents, partners and settlements have pages; expenses, supplier invoices and bank rows open their list with the panel on that row via `?open=<id>`). The list is the accessible form; the picture is `aria-hidden`. The page `/links/<type>/<id>` (`graphAction` for clients; `can(read, link)`) is reached from the *Graph* button next to every *Links* heading (banking panel, invoice page, expense and supplier-invoice panels).

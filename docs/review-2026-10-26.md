# Review 2026-10-26 — the workflow, the decisions, what to change

> Asked for by the owner after the first real use ("the workflow is killing me"): a critical review of what was built since #67 (F56–F94, D35–D57), the decisions included — his own and mine. Findings ranked by impact; each says what, why it is wrong, what to do instead, and the cost. No code in this PR. The target workflow in §2 is written so a spec writer can turn it into `specs/justify/spec.md` in one sitting.

## 0. The one-line verdict

**The app is built document-first; the job is transaction-first.** Every capability the owner needs exists — import, OCR, match, link, derived states, package — but they are arranged around the *document* (upload it, review it, make it something, then go and link it), while the owner's unit of work is the *bank row* ("this went out, here is the proof"). That inversion is the whole of the friction he reports. It is a composition problem, not a rewrite: the services stay, the entry point moves. Everything else below is secondary to this.

```
today    import CSV ─► Documents ─► upload ─► review ─► Make it… ─► Supplier invoices ─► Link payment (a dropdown)
         5 screens, 2 vendor fields, the bank row is the last thing touched

target   import CSV ─► the row ─► [drop the proof] ─► OCR ─► "supplier invoice from Skattepunkten, 1 297.20 — create & link?" ─► done
         1 screen, the bank row is the first thing touched, the document never needs its own page
```

## 1. Findings, ranked

### 1.1 Justify from the bank row — missing (impact: the product)

**What**: there is no way to upload a proof *from* a bank row. The banking panel offers *journal · links · transfer · create rule · raw*; the linking inbox offers *l = Link to…* (pick an existing entity) and *c = categorise*. Creating the proof always starts on `/documents`.

**Why wrong**: the owner's statement of the job ("select a transaction and upload a supplier invoice; DI extracts; done") is the right one. Swedish bookkeeping is proof-per-transaction: the row is the fact, the document is its evidence. The document inbox exists for the other direction (receipts that arrive before their row) and should stay — as the secondary flow.

**Do instead**: a **Justify** panel on the row (banking inbox + transaction panel), one component, five ways out:

```
 Row  2026-07-08  −1 297.20 SEK  "SKATTEPUNKTEN OFFICE"        open
 ┌─ Justify ────────────────────────────────────────────────────┐
 │ ▸ Drop the proof here / choose a file  → OCR → compare card  │  (new)
 │ ▸ Pick a document already uploaded (inbox, scored)           │  (exists: candidates)
 │ ▸ Pick an expense / supplier invoice (scored suggestions)    │  (exists: l)
 │ ▸ No proof needed: fee · transfer leg · tax · salary · …     │  (exists: rules / transfer)
 │ ▸ Create without a document (receipt lost — flagged)         │  (exists: documentMissing)
 └──────────────────────────────────────────────────────────────┘
```

The **compare card** after OCR is the heart of it: *document* 1 297.20 SEK 2026-07-06 Skattepunkten Office Services AB (VAT SE…) vs *row* −1 297.20 SEK 2026-07-08 — amounts equal ✓ · 2 days ✓ · partner match 100 % ✓ → one button **Create supplier invoice & link** (or *expense*, chosen by the document type / the row's sign and the partner's history). One transaction writes: the document's key, the entity (pre-filled from OCR + the row: amount, currency, dates, partner, group = the row's month, payer = the row's account, BAS from the partner default or the rule), `created_from`, `justifies` with the full allocation, and — see 1.3 — the journal entry's partner. Then `j` to the next row. A mismatch (amount off, other currency) still offers the button with the difference shown (card FX, D26), never a block.

**Cost**: M. The pieces exist (`uploadDocumentAction`, `processDocumentJob`, `matchPartners`, `initialFromFacts`, the two dialogs, `applySuggestion`); the new code is the panel, the compare card, one composite action (`justifyWithUploadAction`), the keyboard (`p` = proof). Spec first (FULL lane, D45): `specs/justify/`.

### 1.2 The transaction picker is a dropdown (impact: high)

**What**: *Link payment* on a supplier invoice is a `<Select>` of every open row in the invoice's currency (`supplier-invoice-panel-payments.tsx`); expenses attach the same way. With 3.5 years of rows it is a wall of text.

**Why wrong**: the linking module already scores rows for an entity (`suggestionsForEntity`: amount, date window, reference, partner — with reasons) and renders them (`SuggestionsSection`, used on the invoice page and the banking inbox). The supplier-invoice panel ignores it.

**Do instead**: replace the Select with the suggestions (top 5, reasons, amounts, one click) + a search field (text, amount ±, date) over the rest. Same component on expenses. Delete `payableTransactions` as a UI source.

**Cost**: S. No schema, no strings beyond two.

### 1.3 Two vendors, two truths (impact: high; a decision of mine to reverse)

**What**: a document carries `vendorName` (OCR text, correctable) and the supplier invoice carries `partnerId`; the review page and the invoice can disagree. The same split exists for amounts and dates: the document's *corrections* and the entity's money facts are two editable copies. And **D33** (mine, 2026-10-21) says a `justifies` link never fills the journal entry's partner — so after linking, the row's journal line can still show *no partner* while the invoice two clicks away says Skattepunkten.

**Why wrong**: the owner is right that "vendor ≠ supplier makes no sense". A document is evidence; once it *became* something, the entity is the truth and the document's facts are a reading of it. D33 protected "derived, never typed" for the partner field — but a partner typed on the invoice and then *derived* onto the journal row is exactly what that principle asks for; I applied it backwards.

**Do instead**: (a) **reverse D33 → D58**: the journal entry's partner is derived from the justifying entity when the entry has none typed (read-side rule; a rule-typed partner wins); (b) once a document became an entity, its review form is **read-only with "edit on the supplier invoice"** — the entity's facts are shown on the document page, not a second copy; (c) the match card's *Use match / New vendor* writes the chosen partner's name back as the document's `vendorName` correction, so the two never diverge; (d) the review page stops being a destination in the main flow — it is where you go when the OCR read something wrong.

**Cost**: S for (a) and (c), M for (b) (the review client knows `became` already).

### 1.4 Five menus for one loop (impact: medium, fixed by 1.1 mostly)

Dashboard · Documents · Journal · Banking · Partners · Invoices · Expenses · Supplier invoices · Package · Declarations · Settings (+ Subscriptions). The monthly loop touches three of them in an order the menu does not suggest. With 1.1 the loop lives in **one** place (the banking inbox, already with counts in the sidebar, F72). Then: rename `/banking/inbox` → **Work** (first item, the counts), keep the rest as *records*. The Lakehouse kit (D40) already groups icons; this is a grouping change, not a redesign. Cost: S, nav + strings (serialised).

### 1.5 Subscriptions (F94, D57) — challenge: 4 600 lines for a template (impact: medium)

**What**: a module with periods, dated expected prices, pauses, a matcher, confirm, a timeline, a dashboard to-do, a new link kind `occurrence_of`, five PRs — to stop re-typing the same expense every month for SaaS charges.

**The challenge**: the pain is real (the owner stated it) but the mechanism is large for a solo company with maybe fifteen recurring vendors, and it was specified and built in one day after the workflow problem (1.1) had already been felt. With 1.1 in place, a recurring charge is: row arrives → the proof arrives (by email, see 1.6) → compare card → one key. What a *template* adds on top is the pre-fill (vendor, BAS, group, payer) — which a categorisation rule already carries, and "copy last" already does for supplier invoices. Expected prices, pauses and a period timeline are reporting; they do not reduce clicks.

**Do instead**: do not extend it. Keep it running (it is built and tested) and let **one month of real use** decide: if the owner confirms occurrences from its page every month, it earned its place; if he justifies from the bank row instead, fold the useful part (the template → pre-fill in the compare card) into 1.1 and retire the rest. Record that as the decision: **F94 is on probation until 2026-11-30**.

### 1.6 The proofs arrive by email, and nothing reads email (impact: high; missed feature)

Every SaaS receipt, most supplier invoices and the accountant's own bills arrive as PDF attachments or links in email. Today each one is: open the mail, save the file, go to Documents, upload. **An ingestion mailbox** (`proofs@…` or a plus-address, polled by a small job — IMAP, 15-minute cadence, on the box) → upload with the mail's date and sender → OCR → the row matcher proposes the link → the owner confirms in Work. This is the feature that turns the subscriptions pain into zero clicks and it is one job + one setting (the mailbox credentials, env vars on the box — D51 compliant, nothing leaves). Cost: M. Pair it with **a share target / photo upload from the phone** (PWA manifest `share_target` → the upload action) for paper receipts on the road: S once the upload accepts a photo (it does).

### 1.7 Agents filled time (impact: process)

F70 (base currency per tenant) was built in **9 PRs** and then parked by D46 because no second tenant exists — the constitution's "build for one" was overridden by an agent's thoroughness; F85 then added a guard *for the parked feature*. F66/F67/F77–F80 (read-API refactors, hygiene, converge) were right-sized, but together the week produced ~40 features of which the owner felt none in the flow he uses. **Rule to add** (lessons, project instructions): a row is dispatched only with a *"why now"* written by the owner, and a feature that changes nothing he sees this month waits. The planner session owns this gate, not the builders.

### 1.8 Smaller findings

- **D35** (supplier number unique per supplier, no *Create anyway*) is right. **D37** (open entity = draft) is right and fixes a real pain. **D49/D50** (expense partner) are right and feed 1.1.
- **F93 search** is good; with 1.6 it should also find mails-turned-documents by sender.
- **The document inbox** (my part 2) keeps its purpose for receipts-before-rows, but its *Make it…* should default to "and link to the matching row" when a candidate scores HIGH — today it creates, then the row is linked elsewhere.
- **Private purchases on the company card** (expense, to refund, settlement) work; they should be a *No proof needed → private* choice in the Justify panel that creates the expense with payer = the card account in one step.
- **Journal "partner typed by rule"** stays the way to teach the app (OPENAI → OpenAI); with 1.3(a) the first manual justification can propose a rule ("always OpenAI for OPENAI*?") — one toast, one click.

## 2. The target workflow (for `specs/justify/spec.md`)

```
                      ┌──────────── Work (= /banking/inbox, first menu item, counts) ────────────┐
 Nordea CSV ─► rows ─►│ row ▸ Justify: drop proof │ pick document │ pick entity │ no proof │ lost │
                      │        └─ OCR ─► compare card ─► Create & link (one transaction) ─► next  │
 proofs@… mailbox ───►│ documents inbox (secondary): receipt first, row later → HIGH → auto-propose│
 phone photo ────────►│                                                                          │
                      └────────────────────────────┬─────────────────────────────────────────────┘
                                                   ▼
                       journal (partner derived from the proof, D58) ─► package ─► accountant
```

User stories, in priority: **US1** justify a row with a new file (compare card, create & link, next row); **US2** justify with an existing document / entity (scored, searchable — replaces the dropdown); **US3** no proof needed (fee, transfer, tax, salary, private) with the rule proposal; **US4** the mailbox and the phone feed the documents inbox, HIGH candidates proposed on the row; **US5** the document page after *became* shows the entity's facts, read-only. Success criterion: a month of rows justified without leaving Work, under a minute per row with a proof, under ten seconds per row without.

## 3. AI on the homelab — what is worth it

The box now runs on Proxmox. Two separate questions: reliability (Proxmox's job) and AI (an adapter's job).

**Reliability first, no AI needed**: VM snapshot before every image pull (one line in the update script); off-host backups already (`backup.sh`) — add a restore drill *on a second VM* monthly, automated; Uptime Kuma (or any pinger) on `/api/health`; a **staging VM** that pulls `main`'s image first and runs the smoke test before prod does. Cost: S each, all owner-side, none in the repo beyond the runbook.

**AI — local on the box, by design (the owner, 2026-10-26, correcting my §3 draft)**. The owner wants a *local* model on the Proxmox box for in-app features: the best BAS account, the counterparty behind a bank text (`MSFT * E0100ZW7M8` → Microsoft), spotting mistakes. Local is the right call for AF: D51 says nothing real leaves the box, and these tasks are narrow. The design that keeps it small:

```
 bank row / document ─► 1. rules + history (deterministic, free)  ─► proposal
                        2. local LLM only for what 1 cannot answer ─► proposal (confidence, reason)
 owner confirms in Work ─► the existing service writes ─► and a rule / alias is learned
                            "AI proposes, rules remember" — the model is called less every month
```

- **One adapter**, `kernel/ai`: an OpenAI-compatible chat endpoint (Ollama or vLLM on a Proxmox VM; `AI_BASE_URL`, `AI_MODEL`, `AI_API_KEY` env vars — portability rule, nothing else changes; a hosted model is the same adapter if ever wanted). Structured JSON out, validated with Zod; every call logged with model + prompt version. **It never writes a money fact or a status**: it fills a `proposals` read model (row, kind, proposal, confidence, reason, model, accepted?) that the Justify panel shows pre-filled; accept = the existing service; accept / reject rates per kind on the dashboard are the evaluation.
- **Counterparty → partner**: first a deterministic normaliser (strip the card suffix `* E0100ZW7M8`, `K*`, digits, city) and the alias table learned from confirmations (the categorisation rules already carry partner + category); the model only when no alias matches — "MSFT = Microsoft" is world knowledge a 7B model has; confirming creates the alias, so the second Microsoft row never asks.
- **BAS account**: history first (same partner → its last category, the partner default); the model for a new partner, with the tenant's active BAS list (~40 lines) and the row / document text in the prompt; confidence shown; the owner's pick becomes the partner default.
- **Mistakes**: deterministic checks first and always (net + VAT ≠ total, the same amount twice in a week, an FX difference above the tolerance, a proof whose billed-to is not the company (D53), a missing proof at month end, a subscription price that moved); the model on top for the judgement calls — "this looks private", "this receipt is a restaurant, not travel", "two invoices for one period" — each as a sentence the owner can dismiss.
- **Hardware honestly**: a 7–8B instruct model (Qwen 2.5 / Llama 3.1 class, 4-bit) on CPU with 16 GB RAM answers these short prompts in 2–10 s — fine as a background job after an import or an upload, not inline on a keystroke. A used 12 GB GPU makes it instant and opens a 14B model; reading invoices end to end (a second reader behind Azure DI) needs a vision model and a GPU — keep DI for that. Decide the model after the box's CPU / RAM are known; the adapter does not care.
- **Order**: the adapter + the proposals read model + counterparty → partner first (every row benefits); BAS second; the checks third (the deterministic half ships before any model). Spec with `specs/justify` so the panel is designed for proposals from day one.

## 5. CI — why PRs wait, and what to do

Measured (lessons, #275): a code PR runs lint, typecheck, unit, build and e2e in parallel in **~6.5 min**; the critical path is `unit-test`'s serial server project (**5–6 min** of DB tests on a 2-core runner); `main` runs the same again after each squash merge; the merge watcher is serial. Five PRs for one feature = ten runs ≈ an hour of waiting. Nothing is broken; it is the shape. In order of payoff:

1. **Shard the server tests** (`vitest --shard 1/3 … 3/3`, one Postgres service each; `MIN_RUNS` in the merge script follows the check count) and the e2e (`playwright --shard 1/2`). The repo is public, so Actions minutes are free and up to 20 jobs run at once — parallelism costs nothing. Critical path → **~2.5 min**. S, one workflow PR.
2. **`concurrency: { group: ${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: true }`** — the workflow has none; a push to a branch should cancel the previous run of that branch. One line.
3. **A self-hosted runner on the Proxmox box** — 4–8 cores, warm `node_modules` / Playwright / Docker caches, a local Postgres: the same suite in **~2–3 min** with no queue, and free. Caveat for a public repo: a fork's PR must never reach it — the repo setting *require approval for all outside collaborators* plus `if: github.event.pull_request.head.repo.full_name == github.repository` on the self-hosted jobs, and run it as an ephemeral runner in an LXC / VM restored from a snapshot after each job. Our PRs all come from in-repo branches, so this is safe in practice. M (owner-side), then the workflow points `runs-on` at it.
4. **Fewer PRs per feature**: schema first and alone (serialisation rule), then **one** PR for the rest unless it is a different module. Subscriptions' five PRs were agent habit, not necessity. A line in the project instructions.
5. **Skip `main`'s rerun when nothing changed**: the squash commit has a new SHA, so CI reruns a tree it just tested; the merge script could pass `[skip ci]` in the squash title when the PR head was tested on the same `main` parent, and `main` would then only run the nightly. Defensible, but it removes the "main is green" proof — do 1–3 first and keep this for later.

## 4. What I'd stop, start, keep

- **Stop**: building rows the owner did not ask for *this month*; extending subscriptions; the document page as a destination.
- **Start**: `specs/justify` (1.1 + 1.2 + 1.3 + US3) as the next FULL-lane spec — it is the first real version; the mailbox (1.6) right after; the AI adapter with the assistant once Justify ships.
- **Keep**: everything underneath — the services, the link table, derived states, the package, the kit. None of this review asks for a schema change beyond D58's read-side rule and the mailbox's job table.

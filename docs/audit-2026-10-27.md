# Audit 2026-10-27 — in depth, independent

> The owner's second ask after [[review-2026-10-26]]: "you scratched the surface, oriented by me — challenge every bit: tech, functionality, implementation, UI/UX; what would you have made differently; take your time." Method: five read-only auditors, each on one half of the app (domain model & money · ingestion · UI/UX · tech, security, performance, tests · scope, decisions, process, docs), each told not to repeat the review and to give `file:line` evidence; ~70 findings came back; the ones that drive a decision were spot-checked in the code (marked ✓); then one layer that only the whole shows. Nothing here is a bug report on the owner's data (D51); every example is from the seed or the fixtures.

## 0. The verdict

1. **The app does the job; the shape of the app is four times the job.** ~80 000 hand-written lines, 45 tables, 39 pages, 215 server actions and 1 900 strings in three languages, for one person, one company and about a hundred bank rows a month. Built in seven days (281 commits, 292 PRs, 125 commits on 2026-10-23). The volume is not a side effect — it is the main finding: it is what the owner, a BI engineer, cannot read, cannot review, and will pay for in every change. The question is less "what is wrong" than "what should not exist".
2. **Three auditors who never saw each other's work converge on one structural mistake**: the journal entry is a copy of the bank row (A4, B15, C1). It is the root of the Journal page duplicating Banking, of "linked but not categorised" in the accountant's sheet, of two identities per fact in the link table, and of a dependency cycle hidden behind a dynamic import. One change removes all of them.
3. **The product's own promise — every row justified — is not provable**: a CSV row that fails to parse is dropped and the import succeeds; the running balance Nordea gives on every row is stored and never checked; a month is "proven" from the min/max of the rows that happened to arrive (B4, B5 ✓).
4. **Four production facts need fixing this week, before any feature**: registration is open on the internet (D1 ✓), an unauthenticated proxy route fetches arbitrary local URLs (D2 ✓), a missing OCR key silently invents invoice facts (B3 ✓), and the proofs with a seven-year retention duty live in Microsoft's *development emulator* backed up by a live `tar` (D7 ✓).
5. **Nothing has reached its consumer.** After ~280 merges the accountant has seen zero packages; the one quarterly output that was "100 % ticked" (the Swiss VAT return) shipped five bugs. The process optimised for green CI, and CI tests what the agent wrote with the mocks the agent wrote. About 40 % of the week was the agents' own rework (E1, E8). The next milestone is not a feature: it is one real month, compared with what was filed.

The rest of this document is the evidence, the alternative design in four dimensions (§2), the fix-now list (§3), the findings by area (§4), what to keep (§5), what to cut (§6), a sequence (§7), and the decisions only the owner can take (§8).

## 2. What I would have made differently

### 2.1 Tech — the homelab is the target, not a stop on the way to Azure

- **Storage**: a filesystem driver behind `StorageService` (`STORAGE_DRIVER=fs`, a bind-mounted folder, ~60 lines) and **one authenticated download route** `GET /api/documents/[id]/file` (session → `can()` → RLS → stream). No SAS URL ever reaches the browser, no CORS, no `blob-proxy`, no emulator; backups are `rsync`. Blob stays as the second driver for a cloud deployment that does not exist yet. Today Azurite is the production store (`docker-compose.prod.yml:65-67` ✓) and `scripts/backup.sh:18-20` tars its LokiJS metadata while it runs (D7).
- **Auth**: keep Better Auth and the organisation plugin (built, fail-closed), but **close it**: `disableSignUp` once the owner exists, no organisation creation, `/register` gone; admin by a CLI (`scripts/user.ts create | set-password | add-member`) instead of a members UI (D1, D6). Multi-tenancy and roles stay as defence in depth and stop shaping specs: no "the accountant sees…" scenario in a new spec until an accountant exists (F03 parked by the owner).
- **RLS: keep; drop the FK ban.** The constitution's reason — "cross-table FKs, RLS blocks them" — is false: FK checks bypass RLS, which the repo's own spike proves (`cross-table-rls-spike.test.ts:235`, D-§3). Composite `(tenant_id, id)` FKs give integrity *and* the cross-tenant check; validated UUIDs give neither — see A11 (a cascade that crosses a module boundary unnoticed) and A4 (a join without a key on every list).
- **Drop** Sentry (off on the box by D51, yet 57 MB in the image and wrapping the build), `@tanstack/react-query` (a provider with zero queries), `xlsx` 0.18.5 (unfixable advisories; write the package's sheet with `fflate`, already a dependency, or ship CSV) (D13). **Keep** Next.js + server actions (215 actions behind one middleware chain is a coherent API — a framework change buys nothing), Prisma, pg-boss, Chromium, Vitest + Playwright, Biome.
- **Three dictionaries → one.** The owner reads English; the accountant is parked; `sv.ts` is maintained by agents for nobody. The `i18n` lock in the never-together rule exists only because every string lands three times. Freeze `fr`/`sv` to fall back on `en`, translate once at the end: the lock disappears, every UI PR shrinks by a third, the biggest kernel folder stops growing.

### 2.2 Functionality — what the app should do that it does not, and the reverse

- **Prove completeness.** An import is a statement with an opening and a closing balance; the chain `previous balance + amount = balance` is the proof that no row is missing *inside* an export and *between* two exports. A row that fails to parse fails the import (never `continue`, B5 ✓). The Months grid says "complete to 2026-07-15", never "proven" on half a month (B4).
- **A scorer that can always be applied, with memory.** Today the candidate window is ±5 days around the booking date on the *issue* date (`linking/suggestions.ts:35` ✓), so an invoice paid on 30-day terms — the company's only income — is never a candidate (B1); a cross-currency receipt is scored, then refused on apply (B6); any pair gets 15 points with a false reason (B7); the strongest signal there is — *this counterparty key was linked to this partner before* — is not read (B8). Rules, the scorer and the subscriptions matcher are three engines with three tolerance semantics (B14). One engine: history first (key → partner → BAS → expected amount, learned from every confirmation), then tokens, due-date windows, FX tolerance by instrument. This is the first "AI" layer and needs no model.
- **Incoming rows need proofs too**: a vendor refund, a Skatteverket repayment, an insurance payout can only be a rule today (B12).
- **Two things the Excel did that the app does not** (E6, E7): *Uploaded Accounting* per row — "did the accountant already get this?" — has no equivalent (a derived `packagedIn` per entity and a *changed since v1* flag per month, when a late receipt lands in a built month); and the cash-planning row every invoice had (taxes, salary, what the company keeps) was cut as "Growth" — it is one derived row per invoice.
- **What it should not do**: edit the document as a record. The review page is a form that mirrors the OCR JSON — Category, Type, Vendor, Date, Amount, Subtotal, VAT, Currency, line items with Qty / Unit price / Tax (`f71-review-light.png`) — and *Make it…* then copies the corrected facts into an expense dialog where they are corrected again. Nothing consumes line items. The entity is the record; the document is its proof; the page that edits facts is the entity's.
- **Not yet**: subscriptions as a module (4 613 lines, three tables, a link kind) where a rule with an expected amount and a cadence would do (A-§3, B14) — on probation until 2026-11-30 as the review said; manual journal entries (periodisation is the accountant's job, D1).

### 2.3 Implementation — one transaction table, the link as the only payment record, invariants in Postgres

- **One transaction table.** `journal_entries` duplicates `bank_transactions` field by field (`prisma/schema/journal.prisma:42-56` ✓: date, description, counterparty key, amount, currency, base, rate) and bolts on BAS, partner, note. Put base, rate, BAS, partner, note and the no-proof flag **on the bank row**; the journal becomes a view (`/journal` = the accountant's read of the same rows, or goes). Removes: the `(source_type, source_id)` join without a key on every list; `rowsToJustifyCount` loading every row + link + entry on every navigation (`app/(app)/layout.tsx:64-78`, D8); the two linkable identities of one fact (`links-state.ts:33-46`); the journal → linking → banking → journal cycle behind `await import` (`implicit-rate.ts:37-39`); the Journal page (C1); and B2 — the accountant's sheet printing `basCode: null` on a row whose proof carries 6540. One migration copies six columns; the owner said migration pain is acceptable.
- **The link is the only payment record.** `paid_amount` / `paid_currency` on expenses and supplier invoices duplicate the link's `allocated_amount + currency` and force one row ↔ one entity (A7); a deposit plus a balance, or two receipts on one card row, are refused. The entity's base is written once at its date; each `justifies` link carries `allocated_base`; the FX difference is `Σ links' base − entity base`, signed, derived, one rule for receivables, payables and reimbursements (A5: today only the gain is recognised, the loss is "unallocated"; A8: three conventions for "the SEK of this entity" depending on the payment path).
- **Every invariant that is in a service is also in Postgres.** `sum(allocations) ≤ amount` exists only in TypeScript, read-then-insert without a lock, while the constitution claims "CHECK + service" (`migrations/20261020060000_add_links:20-23` ✓, `linking.ts:221-232`) (A1). D37 promised the money lock on both payables; expenses got the trigger, supplier invoices got a comment (`migrations/20261021160000:90-101`) (A2). One parameterised `lock_money_when_linked(table)`, one allocation-sum trigger, and `tenantMiddleware` rolling back whenever a handler returns an error instead of 19 `throw RollbackError` sites by convention (D12).
- **The money code once.** `baseFor` / `baseAmount` live in expenses, supplier-invoices and journal; `resolveAlias` and `checkVatRegistration` twice; attach / detach pairs near-identical (A9). `kernel/money/base.ts` and one payables helper. Two "is it settled" tolerances (`kernel/money/settlement.ts:9-15` vs `expenses/status.ts:16`, A6) → one.
- **The OCR job state machine is right; what surrounds it is not**: the model follows the *type* the owner picked, not the document — a SaaS PDF uploaded as an expense runs `prebuilt-receipt`, which drops the invoice number and the vendor's tax id, so D35's uniqueness and D53's billed-to check never fire for most of his documents (B9); no `net + VAT = total` check; the mock runs whenever a key is missing (B3); facts live only in JSONB — the partner page cannot show "its documents", search finds key and filename only (B13).

### 2.4 UI/UX — six nouns, one screen

- **Six nouns**: Work · Transactions · Proofs · Invoices (Partners a tab) · Costs (supplier invoices and expenses two tabs of one page) · Month-end (package, Swiss VAT, SCB) · Settings. No Journal, no Subscriptions in the menu; no "Records / Sales / Costs / Close" headings over thirteen items (C14).
- **One screen he lives in — Transactions**: the Months grid on top (the best screen in the app), the table under it with Amount and State pinned, the docked panel opening on **state + the one next action** — today it opens on *As the bank said* with Sender / Recipient / Name / Own notes all "—" and the decision below the fold (`transaction-panel-light.png`, C2); j / k / Enter / n / p / u on the list itself, not in a separate inbox (three inboxes, two keyboard maps, C9); dropping a file on a row is the upload (the review's Justify panel).
- **Forms: three fields above the fold.** The expense dialog asks thirteen questions and the amount is the eighth (C6); the supplier dialog asks net, VAT *and* total. Amount + currency, date, who; the rest derived (category from the partner, payer from the last entry, group = the open trip or the month) or under *More*.
- **One Combobox for every picker** — there is none in the kit; ~40 BAS lines, partners, groups, documents and bank rows are plain `<Select>`s you cannot type into (C3). BAS labels in the UI language (review §6).
- **One vocabulary for one state.** The Months legend and the State column use *Justified · To justify · Proven · Open · Linked · No document needed* — six words for three states (`workbench-light.png`). Real plurals instead of 56 "(s)" strings, enum labels instead of `same_currency` / `bank_statement` / `incomplete_period` on screen (C7); `yyyy-mm-dd` in inputs as in columns (C15); money formatted in one place (C8).
- **Every flag a link, every empty state ends with the next action** (C12); the dashboard a start page (the Months grid and the to-dos that are > 0), not a status page of audit counts and "22 ECB days without a rate" (weekends — a permanent to-do) (C11).

## 5. Keep — the parts that are better than the alternatives

- **The link table and the derived states, in one place**: `deriveTransactionState`, `inboxState`, transfer-as-link (D44), `createLink`'s two-sided allocation and currency checks; immutability and `block_delete_when_linked` as triggers with tests that hit the trigger, not the service.
- **The import's write discipline**: parse → currency guard → dedup by content hash + occurrence (property-tested) → every rate pre-checked → the statement stored as a document → one transaction; `deleteImport` refuses when linked.
- **The OCR job**: ids-only payload, claim → OCR outside any transaction → save, exclusive per document, retries with backoff, dead-letter → `ocr_failed`. Textbook. So are the jobs in general (pg-boss in Postgres, `onCommit` enqueue, singleton keys, catch-up schedules — nothing to operate, survives scale-to-zero).
- **`number_series`** row-locked, taken last in the issuing transaction — gap-free numbering. **Print tokens** (HMAC, path-bound, 120 s, timing-safe). **ECB cross-rates** via EUR with a 4-day cap that refuses instead of guessing.
- **The architecture guard + the Biome grit rule** — the constitution is executable, not prose.
- **The DataTable** (typed Excel-style server-side filters with counts, URL state, per-user layout, Σ footer), **Ctrl K**, **the Months grid**, and **the Lakehouse kit** (tokens that make every dark screenshot right, `StateLabel` icon + word, `formatMoney`, code chips, the invoice edited inside its print layout).
